# LEARNING_LOG.md — append-only AI learnings

> Append-only журнал для новых граблей/инсайтов. AI-агенты пишут сюда **в момент обнаружения** проблемы.
> Раз в неделю (или при значимой версии) релевантные записи переезжают в `MEMORY.md` (раздел «Активные грабли»).
> Цель — не терять знания между сессиями, не раздувая основную память.

### 2026-05-23 — `MEMORY.md` достиг 908 строк (×9 от заявленного)

**Контекст:** Audit проекта по запросу пользователя «обнови файлы проекта и память».
**Грабля:** `MEMORY.md` объявлен как «~5K токенов» в `CLAUDE.md`, фактически 908 строк (~45K токенов). При каждом старте сессии съедает 25%+ контекста Claude Sonnet 200K.
**Причина:** Накопительный bias — каждая версия (v0.10 → v0.22) дописывала свой раздел без удаления предыдущих. Грабли v0.10 v0.20 v0.21 все одновременно «активные».
**Фикс:** Разделить на `MEMORY.md` (текущее состояние, активные инварианты — 321 строка) + `docs/memory-archive/v{X.Y}-v{X.Z}.md` (исторические нарративы по версиям, читаются по запросу).
**Урок:** При обновлении `MEMORY.md` — критически смотреть, что устаревает. Грабли v0.10 удалять/архивировать, если они уже не повторяются с v0.20+. Использовать `git log MEMORY.md` для аудита размера раз в N версий.

### 2026-05-24 — mempalace окончательно сломан (Issue #832), переход на agentmemory

**Контекст:** Пользователь повторно попытался `mempalace migrate --yes` в своём терминале. Команда зависла на стадии «Migrating» после 30+ минут на 148.6MB chroma.sqlite3.
**Грабля:** `mempalace` использует `chromadb.PersistentClient` (embedded SQLite + HNSW). Hooks + sync routines + agent MCP конкурируют за один SQLite — destructive segment locks повреждают HNSW индекс. Это [Issue #832](https://github.com/MemPalace/mempalace/issues/832), уже подтверждено мейнтейнерами.
**Причина:** Архитектурная — chromadb embedded mode не thread/process-safe для concurrent writers. Fix требует standalone Chroma HTTP server (PR в #832, не merged).
**Фикс:** Перешли на [agentmemory](https://github.com/rohitg00/agentmemory) (17K stars, v0.9.21, май 2026). MCP server на localhost:3111, 51 tools, BM25 + Vector (local @xenova/transformers) + Knowledge Graph через RRF. 95.2% R@5 на LongMemEval-S. Storage — local SQLite через `iii-engine v0.11.2` (native Rust runtime, обходит chromadb concurrency проблему).
**Урок:** Embedded vector DB (chromadb, qdrant-embedded, lancedb) — плохой выбор для multi-process AI agent integrations. Использовать либо standalone HTTP server, либо native runtime с правильной concurrency (iii-engine, rocksdb).

**Урок:** **ВСЕГДА читать официальный README**, не только третьесторонние обзоры. Dev.to статьи дают концептуальное понимание, но опускают critical install details. Перед deployment чужого open-source — `git clone` или хотя бы Read raw README.md с GitHub.

### 2026-05-31 — block-level state, который не персистится, тихо сбрасывается

**Контекст:** Блок `unit.ozon-kpi`, селектор «Сравнить с» (`compareMode`).

**Урок:** Любой пользовательский выбор в блоке (не только период) ДОЛЖЕН персиститься в config через `onConfigChange`, иначе тихо сбрасывается. Локальный `useState` — только зеркало config.

### 2026-05-31 — shared pure-логика для server+client: отдельный не-'use client' файл

**Контекст:** Блок `unit.ozon-ai-insights` + новые API-routes + DB schema должны делить тип `Insight` и rule-based генераторы.
**Грабля:** Логика и тип `Insight` жили внутри `'use client'` блока — их нельзя импортировать в server (schema/queries/route) без затягивания React.

**Урок:** Pure-логику/типы, нужные и на сервере, и в client-блоке, держать в отдельном не-'use client' файле; кросс-импорт типов из server-роутов — всегда `import type`.

### 2026-06-01 — доступ к live-значениям блоков из UI вне BlockValuesProvider

**Контекст:** Глобальный «AI Анализ раздела»: кнопка в шапке страницы должна видеть live-значения блоков, чтобы ИИ анализировал реальные метрики, а не только `config`.
**Грабля:** `BlockValuesProvider` оборачивает контент ВНУТРИ `BlockGrid`, а кнопка `SectionAiButton` рендерится в шапке страницы — СИБЛИНГ над `BlockGrid`, т.е. вне провайдера. Прямой `useContext(BlockValuesContext)` из шапки вернёт null.
**Фикс:** Bridge-паттерн через внешний (вне React) store. `PageSnapshotPublisher` монтируется ВНУТРИ провайдера (в `BlockGrid`), читает value-store + live `blocks`, пишет снапшот в module-level `Map<pageKey, ...>` (`src/lib/blocks/page-snapshot.ts`). Модалка в шапке читает снапшот по `pageKey` (get + subscribe). Не пришлось лифтить провайдер на уровень страницы (6 страниц не тронуты).
**Бонус-паттерн:** конвенция `__aiContext` — блок публикует богатый текст для ИИ как служебное `__`-поле в `useBlockValuePublisher`. `useAvailableBlockSources()` уже скрывает `__`-поля, поэтому пикеры источников не засоряются. Универсально: любой блок может дать ИИ-контекст, не меняя API анализа.
**js-tiktoken:** ставить пакет `js-tiktoken` (pure-JS, не wasm `tiktoken`). Использование: `new (await import('js-tiktoken/lite')).Tiktoken((await import('js-tiktoken/ranks/o200k_base')).default)`. Ранги тянуть динамически (client-only), иначе раздувают bundle. Без `.free()` (это у wasm-версии).
**Урок:** Для доступа к реактивному page-state из UI вне его провайдера — bridge-компонент внутри провайдера + module-level external store по ключу, а не лифтинг провайдера. Единая pure-функция сборки контекста (`assembleSectionContext`) для клиент-счётчика и сервер-промпта гарантирует, что счётчик токенов = тому, что реально отправлено.

### 2026-06-02 — кросс-раздельный контекст: только серверный резолв + refs, не доверять телу клиента

**Контекст:** «AI Анализ раздела» — добавить в контекст данные ДРУГИХ разделов (их последний ИИ-отчёт или config блоков).
**Грабля:** другие разделы НЕ смонтированы → их live-значения недоступны в client-side `page-snapshot` store (он наполняется только для текущей страницы). Соблазн: гонять тело отчётов/блоков через клиент в роут.
**Фикс:** клиент шлёт в `analyze-section` только refs `externalSources: [{pageKey, mode}]`; сервер резолвит тело из БД (`resolveExternalSources`: последний `section_ai_reports` или `loadLayout` config). Для превью/счётчика клиент берёт те же данные из `GET /api/ai/context-sources` (та же БД, тот же билдер `buildExternalSourcesContext`) → паритет токенов держится. Безопасность: тело не доверяется клиенту, scoped tenant+user.
**UI-паттерн:** мини-модалка сделана data-driven (`sources/loading/error` пропсами) — родитель делает ОДИН fetch и переиспользует данные и для счётчика, и для модалки (вместо двойного fetch).
**Умный режим:** `resolveMode` — текущий раздел/есть отчёт → `report`, иначе `blocks`. Текущий раздел в списке наравне (его прошлый отчёт можно подмешать; база уже = live-блоки).
**Урок:** Для «контекста из других разделов/страниц» в SaaS с per-page live-state — резолвить на сервере из БД по ref'ам, а клиент использовать лишь для превью через идентичный билдер. Это и безопаснее (нет forgeable payload), и проще (нет синхронизации больших тел).

### 2026-06-02 — «AI Анализ блока»: переиспользование scope-нейтральных примитивов + гибридный контекст

**Контекст:** Кнопка «ИИ Микроагент» блока переработана в двухрежимную модалку (Анализ + Микроагент), хранение отчётов по блоку, контекст из блоков всего проекта, кнопка «Все блоки», анализ раздела по отчётам блоков.
**Переиспользование:** типы инсайтов/парсер (`SectionInsight`, `extractSectionReport`, `InsightCard`) изначально нейтральны к scope → анализ блока построен на тех же примитивах + новые билдеры в `section-insights.ts` (`assembleBlockContext`, `applyBlockReports`). Зеркалил готовую инфраструктуру раздела (table/queries/route/dialog) почти 1:1 с заменой ключа на `blockId` — быстро и консистентно.
**Гибридный контекст (грабля):** пикер контекста «весь проект» = блоки текущего раздела (live из page-snapshot, есть на клиенте) + блоки других разделов (НЕ смонтированы). Решение: текущий раздел шлём live-снапшотами (`liveContextBlocks`, доверяем как контенту страницы), другие — только ref-ами `{pageKey,blockId,mode}`, сервер резолвит из БД (`resolveBlockContextSelections`). Превью токенов на клиенте — по данным из `block-context-sources` (тот же билдер) → паритет.
**Анализ раздела по отчётам блоков:** `applyBlockReports(blocks, map, 'reports')` подменяет сырой `aiContext`/`output` блока на текст его последнего отчёта. Одна pure-функция + общий `GET /api/ai/block-reports?pageKey=` (карта blockId→отчёт) для клиента и сервера → счётчик = реальному промпту.
**React-грабля:** панели в shell-модалке обязательно `key={blockId}` — без ключа state (`parsed`/`query`) не сбрасывается при переоткрытии на другом блоке, показывая чужой отчёт.
**Build-грабля:** после `rm -rf .next` первый `pnpm build` иногда падает с `PageNotFoundError: Cannot find module for page` на этапе «Collecting page data» (flaky worker) — повторный build с тёплым кэшем проходит. Не искать несуществующую ошибку, если typecheck зелёный.
**Урок:** Проектируй «report» примитивы scope-нейтрально (section/block/page) с самого начала — тогда новый scope = новые билдеры контекста + новая таблица с доп. ключом, без дублирования парсера/типов/UI-карточек.

### 2026-06-19 — `/app`-префикс: grep-аудит, а не typedRoutes, — настоящий гейт миграции путей

**Контекст:** добавляли `/app` ко всем внутренним страницам (`(app)→app` сегмент).
**Грабля 1 — typedRoutes НЕ ловит большинство:** `experimental.typedRoutes` включён только при `!isTurbo` (`next.config.mjs`) И валидирует лишь `Route`-типизированные JSX `<Link href>`-литералы. Хардкод-пути в `string`-конфигах (nav-массивы, `command-palette` `go()`, `pageHref(): string`, e-mail HTML, AI-промпт) типам невидимы. Настоящий гейт — grep: `['"\`]/(dashboard|cashflow|...)` (кавычка/бэктик + сразу `/имя-страницы` структурно исключает `/api/...` и `/app/...`).
**Грабля 2 — функциональные пропуски вне кода:** `/cashflow` сидел в AI-промпте (`block-capabilities.ts` `configFormat`) → ИИ продолжил бы генерить мёртвые nav-card URL; и в e-mail `templates.ts` (plain HTML). Оба не ловятся ничем кроме grep по всему `src`.
**Грабля 3 — переменные, собранные из путей:** `const inboxHref = cfg.channelId ? \`/inbox?...\` : '/inbox'` — `string`-переменная в `<Link>`, типы молчат. grep-аудит поймал.
**Механизм:** `(app)` (route-group, без URL) → реальный сегмент `app/` даёт `/app/*` тем же `layout.tsx`. `next.config.redirects()` (выполняется ДО middleware) форвардит старые пути → закладки живы. Персистентные данные (nav-card `config.href` в jsonb) чиним и на рендере (`normalizeNavHref`), и разовым SQL — render-нормализация делает SQL некритичным.
**Урок:** при массовой замене путевых литералов нельзя полагаться на типы/билд — обязателен grep-аудит по всему `src` (вкл. промпты/письма/string-конфиги), а персистентные пути в БД чинить нормализацией-на-рендере + опциональной миграцией.

### 2026-06-19 — Скелетоны: route loading.tsx НЕ покрывает «холодный» вход, пока async-layout сам await'ит БД

**Контекст:** глобальная система скелетонов загрузки (route `loading.tsx` + per-block overlay).
**Грабля (нашёл адверсариальный критик):** `(app)/loading.tsx` — это fallback для **children** layout'а, но сам async `layout.tsx` рендерит эту Suspense-границу и обязан завершиться первым. Пока layout `await`'ит `auth()` + `loadLayout('nav')` + `listPinnedBoards()`, при **первом** (холодном) входе в сегмент пользователь видит старый экран, а не скелет. `loading.tsx` помогает только на навигации ВНУТРИ сегмента.
**Фикс (B0):** статическую оболочку (сайдбар-рамка/хедер) рендерим сразу после дешёвого `auth()` (JWT, без БД); DB-зависимую навигацию выносим в async-компонент под `<Suspense>` со скелет-навигацией. Только тогда холодный вход показывает скелет мгновенно.

**Причина:** бюджет сформулирован в символах, а рекомендованная в правилах команда измеряла байты — метрика и измеритель разошлись.
**Фикс:** в каноне `of-end-session` (и в шапках `MEMORY.md`/`CLAUDE.md`) команда заменена на `LC_ALL=en_US.UTF-8 wc -m` / `python3 -c "print(len(open(...,encoding='utf-8').read()))"` с явным предупреждением про байты.
**Урок:** любой числовой бюджет в правилах задавать ВМЕСТЕ с командой измерения, и проверять, что команда меряет ту же единицу. Для русских текстов `wc -c` и `wc -m` без UTF-8-локали — это байты, а не символы.

### 2026-08-15 — Секрет в argv виден всей системе: `env VAR=... cmd` — это утечка

**Контекст:** обёртка `deploy/pi-status/of-passwd.sh`, написанная как раз для того, чтобы пароли не попадали в историю оболочки.
**Грабля:** запуск вида `sudo -u firay env DATABASE_URL="postgres://user:ПАРОЛЬ@..." pnpm …` кладёт строку подключения в **аргументы** процесса. `/proc/<pid>/cmdline` читается любым пользователем системы, и обычный `ps aux` во время выполнения печатает пароль на экран соседа. То есть скрипт, закрывавший одну дверь для утечки, тут же открывал другую.
**Причина:** привычка «передать переменную окружения через `env`» — на самом деле это argv, а не окружение.
**Фикс:** секрет идёт только двумя путями, оба не argv: без смены пользователя — `export` в собственное окружение процесса (`/proc/<pid>/environ` читают лишь владелец и root); со сменой — временный файл `0600`, который дочерняя оболочка считывает (`.`) в окружение и сразу удаляет. `umask 077` выставляется ДО `mktemp`, иначе файл существует мгновение с открытыми правами. Вариант `sudo --preserve-env` отвергнут: зависит от права `setenv` в sudoers и при его отсутствии молча теряет переменную.
**Урок:** всё, что стоит после имени команды, — публично. Секреты передавать через окружение процесса, файловый дескриптор или stdin; `env VAR=…`, `--password=…`, `-p пароль` — эквивалент публикации.

### 2026-08-15 — Денежный итог, посчитанный поверх `LIMIT`, врёт молча и тем сильнее, чем больше данных

**Контекст:** блок сроков годности склада, метрика «Деньги под риском».
**Грабля:** запрос брал партии с `.limit(300)` и сортировкой по сроку, а сумма считалась `reduce`'ом по уже усечённому массиву. Цифра публиковалась как точная — в интерфейс, в межблочные ссылки и в снапшот для ассистента; признака усечения не было нигде. Партии копятся по одной на каждую поставку, а просроченные не исчезают и при сортировке по возрастанию вытесняют остальные за лимит — то есть занижение не гипотетическое. Тот же дефект нашёлся и в карантине («Выручка мимо себестоимости», `LIMIT 500`).
**Причина:** LIMIT ставится ради витрины (не рисовать тысячу строк), а итог считается по тому же массиву «заодно» — экономия одного запроса ценой неверной цифры.
**Фикс:** итоги — отдельным агрегирующим запросом по тому же `WHERE` без `LIMIT` (`sum(...) FILTER`, `count(*) FILTER`), `LIMIT` остаётся только списку строк; в ответе `totalCount`/`truncated`, в блоке — явная строка об усечении.
**Урок:** LIMIT для списка и агрегат для суммы — разные запросы. Если денежная метрика уходит в UI, в привязки или в AI-контекст, она обязана быть полной либо честно помеченной усечённой. Правило легко нарушить незаметно: в том же диффе рядом лежал правильный образец.

### 2026-08-18 — Перенос данных дев→прод: идентификаторы арендатора не совпадают, дамп «как есть» не годится

**Контекст:** прод на Raspberry Pi стоял пустой; выяснилось, что перенос дев-БД был сознательно отменён 07.08 (решение «ключи Ozon ввожу руками, синкну заново»), но ключи так и не ввели — поэтому данных не появилось ниоткуда. Пользователь попросил перенести всё.
**Грабля:** прямой `pg_dump | psql` невозможен. У дева и прода **разные `tenant_id` и `user_id`** (у прода свои, созданные seed'ом вместе с рабочим паролем), а каждая строка несёт их в себе — восстановление дампа либо создало бы второго арендатора, либо упёрлось бы во внешние ключи. Плюс схемы разошлись на одну миграцию (дев 0014, прод 0015), а на проде уже лежала дефолтная раскладка страницы, конфликтующая по уникальному индексу.
**Причина:** identity-строки создаются на каждой инсталляции отдельно, а данные к ним привязаны по внешнему ключу.
**Фикс:** `COPY … TO STDOUT` на деве → `sed` заменяет ТРИ уникальных UUID (арендатор, пользователь, кабинет) в текстовом потоке → `COPY … FROM STDIN` на проде, с явным списком колонок (тогда лишние колонки прода получают значения по умолчанию, и расхождение схем на миграцию не мешает). Остальные UUID сохраняются как есть — иначе развалятся связи между таблицами. Identity-строки (`tenants`/`users`/`memberships`/`workspaces`) и совпадающие справочники не копируются вовсе; конфликтующая строка удаляется до переноса. Скрипт — `scripts/transfer-dev-to-prod.sh`.
**Урок:** при переносе данных между инсталляциями multi-tenant системы переносить надо ДАННЫЕ, а не identity: подменять `tenant_id`/`user_id`/`workspace_id` на целевые, сохраняя все прочие ключи. Проверять три вещи: расхождение схем (по `information_schema.columns`), конфликты уникальных индексов на приёмнике и **отсутствие исходных UUID после переноса**. И помнить, что секреты в переносимых строках зашифрованы ключом исходной инсталляции — их придётся ввести заново.

### 2026-08-20 — Дыра в аналитике 01–18.08: упавший синк отметил период как загруженный

**Контекст:** после переноса данных на прод пользователь заметил, что в аналитике нет августовских дней. В БД: данные до 31.07 и снова с 19.08, ровно 18 дней пусты.
**Грабля:** дыру создали два безобидных по отдельности решения. (1) `updateAccountLastSync` (`src/lib/marketplaces/queries.ts`) ставит `lastSyncAt: new Date()` **безусловно — в том числе при `status: 'error'`**. (2) Пресет `auto` (`src/components/marketplaces/ozon-sync-presets.ts`) строит окно от `lastSyncAt` и при `diffDays <= 1` схлопывается в «только вчера». Последовательность: синк 19.08 упал → `last_sync_at` всё равно стал 19.08 → синк 20.08 по `auto` увидел «синкались вчера» и запросил ровно один день → окно 01–18.08 не запрашивалось **никогда**, и запросить его было уже некому.
**Причина:** `lastSyncAt` трактовался как «когда последний раз запускали синк», а использовался как «по какую дату у нас есть данные». Пока синки не падают, разницы нет — она проявляется ровно в тот момент, когда что-то сломалось.
**Симптом, который видел пользователь:** дашборд показывал выручку «X ₽» и падение −51,7% к прошлому месяцу. После догрузки — «≈2,5X ₽» и рост +12,8%. То есть **UI уверенно рисовал обвал продаж вдвое, которого не было**; пустых мест на графике не было, дыра выглядела как настоящий спад.
**Фикс:** (1) при ошибке `lastSyncAt` не двигается — сохраняется время последнего УСПЕШНОГО синка; (2) окно `auto` считается от **фактического покрытия данными** (`max(date)` в `ozon_analytics_daily`), а не от таймстампа запуска, — теперь любая дыра, от любой причины, затягивается следующим же синком. Догружено вручную: 01–19.08 и отдельно потерянный 14.07; за 18.02–19.08 пропусков не осталось.
**Урок:** «когда мы последний раз пытались» и «по какую дату у нас данные» — разные величины, и подменять вторую первой опасно именно при сбоях, то есть тогда, когда цена ошибки максимальна. Любой инкрементальный загрузчик должен определять, что догружать, по факту наличия данных, а не по журналу собственных запусков. И отдельно: пропуск в данных не выглядит как пропуск — он выглядит как достоверное падение метрики.

### 2026-08-20 — Отчёт о реализации: 400 от API, проглоченный в console.warn, и схема от прошлой версии

**Контекст:** таблица `ozon_realization` пуста и в деве, и на проде, хотя стейдж `realization` входит в `OZON_FULL_STAGES` и выполняется при каждом полном синке. На этой таблице должен строиться отчёт о прибылях (этап D1) — то есть следующий этап плана стоял на данных, которых никогда не было.

### 2026-08-20 — Красный прогон тестов как питательная среда для дефектов

**Контекст:** разбирая дыру в аналитике, обнаружил, что 11 проверок в `scripts/test-ozon-{perf-period,analytics}.ts` падают **постоянно, с v0.18.3**, независимо от текущих правок.
**Грабля:** все 11 оказались устаревшими ожиданиями — производственный код был прав. Семь отстали от осознанного изменения поведения (`completeDayLag`: Perf API отдаёт цифры только за закрытые дни, поэтому правая граница окна — вчера); четыре были TZ-хрупкими: сравнивали UTC-полночь московской даты с локальными геттерами и проходили только при TZ ≥ UTC, то есть «работали» на машине автора и падали в другом поясе.
**Причина:** поведение меняли, тест не трогали. Дальше сработал эффект привыкания: на фоне десятка привычных красных строк новая красная строка не выделяется.
**Последствие, ради которого это стоит записать:** ровно в этом прогоне жил стейдж `realization`, который не загрузил ни одной строки **ни разу за всё время существования** — а на нём должен был строиться отчёт о прибылях, следующий этап плана. Дефект был виден в логах при каждом синке.
**Фикс:** каждую из 11 проверок разобрали отдельно с вопросом «кто прав — код или тест», а не подгонкой ожиданий под текущее поведение. Ожидания обновлены с комментарием о ПРИЧИНЕ (чтобы следующий читатель не «починил» обратно), тесты сделаны детерминированными (заморожен `now`) и прогнаны под четырьмя часовыми поясами.
**Урок:** красный прогон надо чинить в тот же день, когда он покраснел, — не ради дисциплины, а потому что зелёный прогон это единственный дешёвый детектор новых поломок; красный превращает его в шум. И чинить, задавая по каждой проверке вопрос «кто прав», иначе «починка» тестов стирает настоящие баги.

## Как использовать

**Когда писать:**
- Натолкнулся на проблему/грабли, которой не было в `MEMORY.md` → запись в LEARNING_LOG.
- Обнаружил полезный pattern → запись.
- Сделал нетривиальный фикс → запись.

**Когда чистить:**
- При релизе минорной версии — пройтись по LEARNING_LOG, релевантные сжать и перенести в `MEMORY.md` («Активные грабли»).
- Устаревшие (фиксили в коде, больше не воспроизводится) — удалить из LOG, оставить запись в `docs/memory-archive/`.

**Никогда не делать:**
