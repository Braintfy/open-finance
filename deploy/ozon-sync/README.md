# deploy/ozon-sync — ежедневная синхронизация Ozon

Раз в сутки сама подтягивает данные Ozon по всем подключённым магазинам. Без этого синк происходит только когда человек нажал кнопку в браузере: пропустил неделю — в аналитике дыра, а дашборд показывает «падение выручки», которого не было.

| Файл | Что это |
|---|---|
| `../../scripts/sync-ozon-daily.ts` | сам прогон: обходит активные Ozon-аккаунты, создаёт job, зовёт `runFullSync` |
| `of-ozon-sync.service` | одноразовый запуск скрипта под systemd (`Type=oneshot`) |
| `of-ozon-sync.timer` | расписание: **05:30 МСК** ежедневно, с разбросом до 15 минут |

## Почему 05:30

- **Бэкап БД идёт в 03:30** (crontab пользователя `firay`) — к 05:30 он давно закончился, за диск не деремся.
- **Сутки у Ozon закрыты.** Аналитика за вчера к этому времени доступна. Даже если реклама за вчера доедет позже — окна у стейджей скользящие (30/62/90 дней), следующий прогон перезапишет день целиком. Пропущенных данных не остаётся, поэтому гнаться за «самым свежим» часом смысла нет.
- **Не пересекается** с `apt-daily` (~02:40) и `apt-daily-upgrade` (~06:10).
- **Готово к утру** — открываешь дашборд, данные уже свежие.

`Persistent=true` означает: если в 05:30 плата была выключена, запуск не потеряется — отработает после загрузки. `RandomizedDelaySec=900` размазывает старт, чтобы не бить в одну секунду с чужими задачами.

## Установка

```bash
cd /home/firay/open-finance

# 1. Сначала проверка — ничего не пишет и в Ozon не ходит
pnpm tsx scripts/sync-ozon-daily.ts --dry-run

# 2. Юниты
sudo install -o root -g root -m 0644 deploy/ozon-sync/of-ozon-sync.service /etc/systemd/system/
sudo install -o root -g root -m 0644 deploy/ozon-sync/of-ozon-sync.timer   /etc/systemd/system/
sudo systemctl daemon-reload

# 3. Включаем ИМЕННО таймер (сервис включать не надо — его запускает таймер)
sudo systemctl enable --now of-ozon-sync.timer

# 4. Убедиться, что расписание встало
systemctl list-timers of-ozon-sync.timer
```

## Как посмотреть, что происходит

```bash
systemctl list-timers of-ozon-sync.timer          # когда следующий запуск и когда был прошлый
systemctl status of-ozon-sync.service             # чем кончился последний прогон
journalctl -u of-ozon-sync.service -n 200 --no-pager
journalctl -u of-ozon-sync.service --since "3 days ago"
journalctl -u of-ozon-sync.service -f             # смотреть вживую
```

В журнале по каждому магазину видно: когда был прошлый синк, какой job создан, сколько стейджей отработало и с чем, сколько записей и сколько это заняло. Стейджи с ошибками и предупреждения (`⚠`) печатаются отдельными строками.

**Код возврата** (его и показывает `systemctl status`):

| Код | Когда |
|---|---|
| 0 | всё синхронизировано, либо пропущено потому что синк уже шёл |
| 1 | хотя бы один магазин упал (исключение или `job.status='error'`) |
| 2 | не запустился: нет `DATABASE_URL`, битые аргументы |

Частичный синк (`partial` — часть стейджей упала, часть прошла) намеренно **не** делает юнит красным: у Ozon регулярно отваливается то реклама, то `/v1/analytics/data` с лимитом 1 запрос в минуту, и постоянно красный статус быстро перестают читать. Такие прогоны видны в журнале строкой `частично: N` со списком стейджей. Нужно строже — добавьте `--strict` в `ExecStart`.

## Запустить разово руками

```bash
# через юнит — с теми же env и в том же окружении, что и по расписанию
sudo systemctl start of-ozon-sync.service
journalctl -u of-ozon-sync.service -f

# или напрямую (скрипт сам подхватит .env.production)
cd /home/firay/open-finance && pnpm tsx scripts/sync-ozon-daily.ts
```

Полезные флаги:

```bash
pnpm tsx scripts/sync-ozon-daily.ts --dry-run              # только показать план
pnpm tsx scripts/sync-ozon-daily.ts --account=<uuid>       # один магазин
pnpm tsx scripts/sync-ozon-daily.ts --tenant=<uuid>        # один арендатор
pnpm tsx scripts/sync-ozon-daily.ts --stale-minutes=30     # другой порог «мёртвого» job'а
pnpm tsx scripts/sync-ozon-daily.ts --help
```

## Как выключить

```bash
sudo systemctl stop of-ozon-sync.timer          # до перезагрузки
sudo systemctl disable --now of-ozon-sync.timer # насовсем
```

Удалить совсем:

```bash
sudo systemctl disable --now of-ozon-sync.timer
sudo rm /etc/systemd/system/of-ozon-sync.{service,timer}
sudo systemctl daemon-reload
```

Ничего чистить после этого не нужно: скрипт не оставляет состояния на диске, только строки в `ozon_sync_jobs`.

## Два синка одновременно — чем это грозит и как закрыто

Приложение работает **одним процессом**, и лимитер Ozon (40 запросов в секунду на `Client-Id`) живёт **внутри этого процесса**. Скрипт таймера — отдельный процесс со своим счётчиком. Запустятся оба одновременно — суммарно уйдёт до 80 RPS, Ozon начнёт отдавать 429, backoff растянет синк, часть стейджей упадёт. Плюс два `runFullSync` пишут в один и тот же job-набор и портят друг другу прогресс.

**Что сделано:** перед запуском скрипт смотрит `ozon_sync_jobs` этого аккаунта (запрос скоуплен `tenant_id` + `account_id`). Если есть job в `pending`/`running` — магазин пропускается со строкой в журнале, ничего не создаётся.

**Подвисшие job'ы.** Job в статусе `running` остаётся таким навсегда, если процесс-владелец умер: перезапуск приложения при деплое, `TimeoutStartSec`, падение платы. Такой job навсегда заблокировал бы ежедневный запуск — ровно та беда, ради которой таймер и заводится. Поэтому в `ExecStart` стоит `--take-over-stale`: job без прогресса дольше 90 минут считается брошенным, закрывается как `error` (запись тоже tenant-скоуплена) и синк идёт дальше. Полный синк одного магазина занимает минуты, так что живой прогон под этот порог не попадает. Не нравится автоматика — уберите флаг из `ExecStart`, тогда такие случаи придётся разбирать руками (в журнале они помечены `⚠ подвисший job`).

**Чего скрипт не может.** Обратная защита не стоит: `POST /api/marketplaces/accounts/[id]/sync` активные job'ы не проверяет, так что человек всё ещё может нажать «Синхронизировать» в браузере поверх идущего прогона таймера. На практике это маловероятно (05:30), но если понадобится закрыть — тот же самый предполётный запрос нужно добавить в route. Правка не сделана намеренно: она заодно запретит и легитимный сценарий «досинхронизировать один стейдж, пока идёт полный синк».

**Кэш аналитики.** Ответы блока аналитики кэшируются на час **в памяти веб-процесса** (`src/lib/redis.ts` — in-memory заглушка, не настоящий Redis). Скрипт — другой процесс, сбросить этот кэш он не может. То есть данные, записанные в 05:30, веб-процесс может отдавать из старого кэша ещё до часа. При запуске ночью это никого не задевает, но если гонять синк среди дня — учитывайте.

## Что скрипт делает с правами и арендаторами

Задача системная, сессии нет, поэтому `tenant_id` берётся из строки аккаунта — **это единственный запрос без tenant-фильтра**, он помечен `// cross-tenant:` (см. `docs/TENANT_SCOPING.md`). Все дальнейшие обращения — job'ы, поиск пользователя, `runFullSync` — скоуплены именно этим `tenant_id`.

«От чьего имени» идёт синк: берётся `marketplace_accounts.user_id` — тот, кто подключил интеграцию, если он всё ещё состоит в арендаторе. Иначе владелец арендатора (`memberships.role='owner'`), иначе самый ранний участник. Этот `userId` уходит только в авторство новых строк `unit_products`; доступ определяется `tenant_id`, а не им.

Тоггл `syncSettings.autoSyncEnabled` в настройках магазина скрипт **не смотрит** — это остаток UI под так и не написанный BullMQ-воркер, и у всех магазинов он в `false`. Гейт по нему означал бы, что таймер молча ничего не делает. В журнале это отмечено строкой-примечанием.
