# ROADMAP_V2.md — от личного инстанса к публичному продукту

> Составлен 2026-08-12 после закрытия `LK_V2_PLAN.md` (этапы 0–4 в проде, v0.50.0 на Raspberry Pi).
> Основан на мультиагентной разведке (9 агентов): референсы «Синий Рассвет» (`/calc/ozon.html`, `/calc/ozon_multi.html`, `/calc/yandex.html`) и `truestats.ru`, аудит нашей юнитки/аналитики/готовности к публичности/обвязки, разведка сайтов бизнеса.
> Канон исполнения: субагенты Opus 5, оркестрация и ревью — Fable. Каждый этап: реализация → `of-verify` → `of-review` → CHANGELOG → деплой (`of-deploy-pi`).

## Куда идём

Три параллельных вектора, сходящихся в одну точку:

1. **Инструмент должен считать правильно** — сейчас на нём принимают реальные решения по закупкам и ценам.
2. **Инструмент должен оцифровать весь бизнес** — не только Ozon, но и `shopb.example` / `shopa.example`, единые остатки, продажи, себестоимость, деньги.
3. **Инструментом должны пользоваться посторонние люди** — а значит роли, квоты, изоляция, биллинг, документация, гостевой режим.

Порядок исполнения выбран так, чтобы каждый этап давал пользу сразу, а не «через три этапа».

## Этап A — корректность расчётов (P0, в работе)

**Зачем:** сравнение с эталонным калькулятором выявило не пробелы в фичах, а **ошибки формул**. По ним уже принимались решения.

Подтверждённые расхождения (Ozon): прямая логистика не делится на % выкупа (занижение ~30% при выкупе 77%); НДС начисляется сверху вместо извлечения из цены покупателя; соинвест уменьшает расходы и раздувает прибыль; «быстрая отгрузка FBS» у нас **добавляет** 2% к комиссии, тогда как в реальности это **скидка** до 3%; `highVolumeDiscount` снижает логистику на 15% вместо скидки 3 п.п. к комиссии за локальность; приёмка FBO не моделируется вообще; УСН Д-Р при пустых документированных расходах облагает налогом всю выручку.

Яндекс: прибыль считается от цены покупателя вместо цены продавца; спецтариф складывается с комиссией вместо замены; выдуманная статья `fulfillmentCost()`, которой нет в тарифах ЯМ; нет средней мили по литрам, возвратов и хранения невыкупа.

**Шаги:** ① проверить каждое расхождение по коду (разведка могла ошибиться) → ② починить движки `ozon/calculate.ts` и `yandex/calculate.ts` → ③ починить два расчётных бага мульти-таблицы (мёртвая колонка «Выкуп %», неверный `totalStockValue`) → ④ эталонные smoke-тесты с зафиксированными ожиданиями + микротесты на каждый фикс → ⑤ показать пользователю, как изменились цифры на его типовых кейсах.

**Готово, когда:** `scripts/test-unit-economics.ts` и новый `scripts/test-yandex-calc.ts` зелёные, расхождения с эталоном объяснены, влияние на цифры задокументировано.

## Этап B — тарифы: глубина и управляемость

**Зачем:** наши тарифы — аппроксимация публичных формул, зашитая в код и не обновлявшаяся с апреля. У эталона — полная матрица.

| | У нас сейчас | Эталон |
|---|---|---|
| Логистика Ozon | 43 объёмных тира × множитель 1.25 за нелокальность (~1 200 ставок) | 43 тира × 28 кластеров отправления × 31 доставки, отдельно для ≤300 ₽ и >300 ₽ (~37 000 ставок) |
| Комиссии | ручной ввод `commissionPct` | справочник 9 308 категорий с автоподстановкой |
| Яндекс | апрельский пак | справочник 11 028 категорий, тарифы с 01.07.2026 |

**Шаги:** ① модель тарифного пака как данных (не кода) с версией и датой действия, ленивая загрузка тяжёлых справочников отдельным чанком/эндпоинтом → ② импорт матрицы логистики и справочника категорий, поиск категории с автоподстановкой ставки → ③ переключатель «эпохи» тарифов (до/после 28.08.2026) → ④ маршрутизация «из ближайшего прогруженного кластера» вместо плоского множителя → ⑤ UI обновления тарифов в админке + отметка «тарифы устарели» в блоке.

**Наше преимущество, которое надо использовать:** у эталона доли кластеров вбиваются руками, у нас есть живой синк Ozon — доли можно считать по фактическим продажам.

## Этап C — юнитка: удобство и сценарии

**Зачем:** функционально мы уже близко, но каждый расчёт приходится собирать заново.

**Шаги:**
1. **Профиль бизнеса** — единые `taxMode`, `taxRatePct`, `vatPct`, `acquiringPct`, `drrPct` на воркспейс вместо дублирования в config каждого блока.
2. **Пресеты калькуляторов** (`BLOCK_PRESETS` для `unit.*`) — «Ozon FBO локальный», «Ozon FBS», «ЯМ FBY» с осмысленными дефолтами.
3. **Оживить сохранённые расчёты** — схема `unit_calculations`, queries и роут уже написаны, но из UI не вызываются ни разу: история расчётов, сравнение версий, «вернуться к варианту».
4. **Обратный расчёт** — «какая нужна цена под целевую маржу / ROI», расчёт партии к закупке со сроком окупаемости.
5. **Сравнение сценариев** бок о бок (цена/схема/кластеры) — то, ради чего сейчас копируют вкладки.
6. **Оптимизатор кластеров** (есть у эталона, у нас нет) — перебор сценариев прогрузки по суммарной прибыли; на наших данных о продажах он точнее, чем у них.
7. **Экспорт в Excel** для калькуляторов и аналитических таблиц (сейчас только cashflow).
8. Устранить дублирование: `Metric` скопирован в двух блоках, `summarizeClusters` — в двух, две расходящиеся реализации ячейки ввода.

## Этап D — финансовый контур (самый большой пробел)

**Зачем:** это ядро продукта конкурентов и наш главный минус. Маржа у нас = `цена − себестоимость`, реальные расходы в ней не участвуют. При этом **`ozon_realization` уже синкается, но её не читает ни один блок** — деньги буквально лежат в базе неиспользованными.

**Шаги:**
1. **ОПИУ / P&L по периодам** — водопад «выручка → комиссия → логистика → хранение → реклама → штрафы → налоги → чистая прибыль» из `ozon_realization` + `ozon_transactions`; разрезы: магазин / бренд / товар / период.
2. **Себестоимость по партиям (FIFO)** вместо плоского `costRub` + «капитализация склада» (сколько денег заморожено в товаре). Без этого COGS врёт при меняющихся закупочных ценах.
3. **Платёжный календарь и прогноз денег** — развитие cashflow «вперёд, а не назад»: график выплат Ozon (15-е и последнее число), подсветка кассовых разрывов.
4. **Операционные расходы вне маркетплейса** с разнесением на товар/бренд/период — чтобы юнитка видела не только маркетплейсовые статьи.
5. **План-факт** — цели по выручке/прибыли на период и на товар, % выполнения, отклонения.

## Этап E — аналитика Ozon: от «заказов» к полной картине

Мы уже сильны в рекламе и остатках. Не хватает данных, которые Ozon отдаёт, а мы не берём.

**Шаги:**
1. **Категории и бренды** — в `unit_products` нет ни категории, ни бренда (`/v4/product/info/attributes` + дерево категорий). Это сквозное измерение для всех блоков; при 200+ SKU плоская таблица нечитаема. Дёшево и сразу заметно.
2. **Возвраты как сущность** (`/v1/returns/list`) — причины, стоимость, разрез по складам. Сейчас есть только счётчик из статуса заказа.
3. **Реальная маржинальность по SKU** — с учётом комиссии, логистики, рекламы и возвратов (сейчас `цена − себестоимость`).
4. **Органическая воронка карточки** — из `/v1/analytics/data` берём 5 метрик из ~30 доступных; нет показов/переходов/добавлений в корзину и конверсий, вся органика невидима.
5. **Дни запаса по кластерам и план поставок** — сейчас запас считается только глобально; нужны supply-order'ы и расчёт «сколько и в какой кластер везти».
6. **ABC×XYZ** — ABC есть только по выручке; нужны ABC по прибыли и стабильность спроса.
7. **Автосинхронизация** — `autoSyncEnabled`/`autoSyncCron` в схеме есть, воркера нет; нужен ежедневный инкрементальный синк (и это же снимет 300-секундные блокировки web-процесса).
8. **Алерты и утренний дайджест** (Telegram/email) с порогами и тихими часами — аналитика без push не читается.
9. Долги: расхождение расхода на рекламу ~9% (`docs/OZON_ADS_GAP.md`), стейдж «поисковые фразы» — заглушка (блок физически не может работать).

## Этап F — цифровизация всего бизнеса

**Что известно из разведки:** оба магазина — `<shops-dir>/shopb-site` и `<shops-dir>/shopa`, один стек (Next.js 14 + Prisma 5 + **SQLite-файл**), PM2+nginx на VPS Beget, деньги в копейках. Продажи лежат в `Order`/`OrderItem`/`Product.stock`/`ProductVariant`, плюс 1 031 импортированный заказ WooCommerce за 2022–2026 (<оборот>). Каналов больше, чем предполагалось: выгрузки в `<папка выгрузок>` показывают **Ozon, Wildberries, Яндекс.Маркет, ЮKassa, Т-Касса, СБП**.

**Два критичных факта:** себестоимости в базах сайтов **нет вообще**, а поля `Product.ozonSku`/`wbSku` существуют, но **не заполнены ни у одного из 79 товаров** — сшивки «товар сайта ↔ SKU маркетплейса» физически не существует.

**Шаги:**
1. **Реестр товаров и соответствий** — единая карточка товара в Open Finance и маппинг `site.sku ↔ ozon.offer_id ↔ wb.nmId ↔ yandex.shopSku`; UI сопоставления с автоподбором по названию/штрихкоду (79 позиций — разово руками, дальше поддерживать).
2. **Коннектор сайтов** — read-only экспорт заказов/остатков (способ выбирается: эндпоинт с API-ключом / ночная выгрузка / реплика), таблицы `store_*` по образцу `ozon_*`.
3. **Единый склад** — остатки по всем точкам хранения: склады Ozon (FBO/FBS уже есть), собственный склад, остатки сайтов; резервы и товар в пути.
4. **Единые продажи** — заказы всех каналов в одной модели с правилом признания выручки и учётом возвратов/отмен.
5. **Себестоимость и закупки** — приход товара (поставщик, дата, количество, цена), партии, FIFO; отсюда же питается Этап D.
6. **Сводный дашборд бизнеса** — выручка/прибыль/остатки по каналам в одном месте, план поставок с учётом всех каналов.

## Этап G — подготовка к публичному открытию

**Состояние:** базовый security-слой закрыт (rate-limit, CSP/HSTS, шифрование секретов, tenant-изоляция review-gate, 152-ФЗ). Не готово всё, что нужно «для чужих людей».

**Блокеры (без них открывать нельзя):**
- Дефолтные креды seed-админа; принудительная смена пароля при первом входе.
- 2FA для админских ролей (колонка `users.two_factor_enabled` есть, реализации нет).
- Инвалидация сессий: JWT живёт 30 дней и переживает удаление аккаунта и понижение роли.
- Квоты и лимиты на tenant (блоки, строки, вложения, AI-токены); rate-limit на синки и импорты.
- Фоновая очередь для синков и OCR — сейчас 300-секундные операции блокируют web-процесс; на Pi при нескольких пользователях это ляжет.

**Продуктовое:**
- **Роли внутри кабинета** — `memberships.role` (owner/admin/manager/accountant/viewer) объявлена в схеме и **нигде не проверяется**; совместной работы нет.
- **Гостевой/демо-режим** — публичное демо с обезличенными данными; лидмагнит-калькулятор без регистрации (наши калькуляторы технически готовы, нужна только публичная страница).
- **Онбординг** — сейчас заглушка на один экран.
- **Биллинг** — только мок; нужны таблицы, провайдер, вебхуки с идемпотентностью, тарифные планы.
- **Админка** — половина ссылок ведёт в 404 (`/settings`, `/users`, `/billing`, `/audit`).
- **Документация для людей** (не для агентов): руководство пользователя по блокам и кабинетам, инструкция администратора, FAQ по подключению Ozon, политика и оферта, что делать при проблемах.
- Бэкапы с проверкой восстановления, мониторинг, канал поддержки.

## Порядок исполнения

**A → C(1,2,3) → D(1) → E(1) → F(1,2) → B → остальное C/D/E → F(3-6) → G**

Обоснование: сначала правильные цифры (A), затем дешёвые улучшения удобства, которые ежедневно экономят время (профиль бизнеса, пресеты, история расчётов), затем P&L из уже имеющихся данных (D1 — большой эффект, данные лежат готовые), категории/бренды (E1 — дёшево, влияет на все блоки), реестр товаров и коннектор сайтов (F1–F2 — фундамент цифровизации). Тяжёлые тарифные матрицы (B) — после, они трудоёмки и не блокируют остальное. Публичный запуск (G) — последним, когда продукт стоит того, чтобы его показывать.

## Открытые вопросы к пользователю

1. **Себестоимость** — где сейчас ведётся (Excel / 1С / нигде)? Нужен ли FIFO по партиям или достаточно средневзвешенной?
2. **Каналы** — Wildberries и Яндекс.Маркет активны сейчас? Какая доля выручки? Нужны ли коннекторы к ним (есть ключи?).
3. **Доступ к данным сайтов** — предпочтителен экспорт-эндпоинт на сайтах, ночная выгрузка базы или что-то ещё? Есть ли сетевой путь Pi ↔ Beget (белый IP / туннель)?
4. **Признание выручки** — по дате заказа, оплаты или отчёта о реализации?
5. **НДС 5% с 2026** — суммы на сайтах и маркетплейсах с НДС или без? Хранить netto/brutto по каждой строке?
6. **Опт (B2B)** — включать в общую картину продаж?
7. **Публичный запуск** — целевая аудитория и модель (бесплатно / подписка / self-hosted open source)? От этого зависит объём Этапа G.
