# SITES_HUB_ARCHITECTURE.md — хаб как центр: остатки и заказы сайтов

> **Канон с 2026-11-18.** Решение владельца, дословно: «хаб и сервер, который будет на проекте опенфинанс, управляют всем, сайт и остатки им только читаются, либо напрямую с озона, либо с хаба поверх (например офлайн остатки) — сайт отдаёт в хаб свои изменения. Короче, сервер будет головой и центром».
> Документ уточняет этапы 3–4 `docs/HUB_PLAN.md` и заменяет в них всё, что касается сайтов и остатков. Составлен в сессии ShopA по чтению кода трёх репозиториев (хаб — коммит `91e2275`; сайты ShopA и ShopB; служба склада — `shopb-site/deploy/inventory/`). Номера строк перепроверять перед правкой. Вторая редакция того же дня — после двух независимых проверок (раздел 13).

## 1. Решение и границы

- **Хаб — голова.** Единственный источник истины по физическому остатку своего склада и **единственный писатель остатков в маркетплейсы** (Ozon FBS, позже WB). Никакая другая система остатки в Ozon не пишет.
- **Сайты остатки только читают.** Свои изменения — брони, оплаты, отмены, возвраты и деньги заказов — отдают хабу.
- **Источник остатка товара на сайте — один из двух** (свойство пула, см. §5):
  - `ozon` — напрямую из Ozon, как сейчас (служба склада читает свободный остаток FBS и вычитает продажи сайта);
  - `hub` — число хаба: офлайн-остаток своего склада, ручной остаток, единый остаток по каналам.

## 2. Почему между хабом и сайтами нужен пограничный узел

- Хаб — Raspberry Pi в домашней сети: входящих соединений нет (`HUB_PLAN.md:117`), бывают простои (сейчас — переустановка на новый диск, `HUB_PLAN.md:147`), домашний адрес динамический.
- Сайты — круглосуточно на VPS SpaceWeb (`<vps-ip>`). Оформление заказа не может ждать ответа Pi: выключенный роутер дома не должен останавливать продажи.
- Поэтому рядом с сайтами остаётся **пограничный узел** — уже работающая служба склада `stores-inventory` (Python, SQLite, `127.0.0.1:3090`; код — `shopb-site/deploy/inventory/`). Сейчас она хранит пулы (пара «оффер Ozon + склад»), замеры Ozon, брони обоих сайтов в одной транзакции (`BEGIN IMMEDIATE`) и неизменяемый журнал движений. В новой схеме она:
  - хранит **последний план хаба** по каждому пулу и считает по нему доступное сайтам;
  - принимает брони сайтов локально и мгновенно (последняя единица уходит одному покупателю — это уже гарантировано);
  - копит **журнал событий для хаба** (движения по пулам с монотонным номером) и отдаёт его по курсору;
  - для пулов в режиме `ozon` по-прежнему читает Ozon;
  - **никогда не пишет в маркетплейсы** — константа `providerWritesEnabled:false` остаётся правдой, контракты сайтов с `z.literal(false)` не ломаются.

```
         Pi (дом, без входящих)                         VPS SpaceWeb (24/7)
 ┌─────────────────────────────┐ SSH-туннель   ┌──────────────────────────────────────┐
 │ ХАБ open-finance             │──────────────▶│ stores-inventory (пограничный узел)   │
 │  склад: журнал stock_moves   │  pull события │  пулы, план хаба, брони, журнал       │
 │  распределение по каналам    │  push планы   │        ▲ брони/оплаты/отмены (outbox) │
 │  писатель остатков Ozon/WB   │               │        │                              │
 │  P&L, налоги, закупки        │  pull заказы  │  shopa.example   shopb…         │
 └──────────────┬──────────────┘──────────────▶│  экспорт заказов и каталога для хаба  │
                │ Seller API (чтение и запись)  └──────────────────────────────────────┘
                ▼
              Ozon (FBS/FBO), позже WB
```

## 3. Связь Pi ↔ VPS

- Соединения открывает только Pi. **Рекомендация для данных — постоянный SSH-туннель `-L` с Pi** на отдельную учётку VPS без оболочки, с `permitopen="127.0.0.1:3090","127.0.0.1:3000","127.0.0.1:3001"` и `command="/usr/sbin/nologin"`. Ограниченная учётка по тому же приёму уже работает на этом VPS у туннеля камер (`shopa/projects/office-cameras/deploy/install_vps.py`). Новый порт в ufw не нужен (открыты 22/80/443), служба и сайты остаются на `127.0.0.1`.
- **Службу к адресу WireGuard не привязывать.** Сейчас у неё один сокет `('127.0.0.1', port)` (`inventory_service.py:206`); если привязать её к адресу туннеля, а туннель на старте не поднят, служба не стартует, и оба сайта показывают «Наличие уточняется». Если WireGuard всё же выбран — отдельный слушатель на `0.0.0.0:<порт>` и `ufw allow in on <wg-интерфейс>`, а на Pi `AllowedIPs` только `/32` VPS (иначе трафик Ozon пойдёт через VPS) и подсеть, не пересекающаяся с `192.168.31.0/24` и сетями Docker.
- Доступ человека к хабу с телефона (вопрос 5 `HUB_PLAN.md`) — отдельный вопрос, от транспорта данных не зависит.
- Публичный HTTPS для выгрузок сайтов — только запасной вариант (больше поверхность).
- **Токены.** Токен хаба для службы — отдельная переменная `INVENTORY_HUB_TOKEN`: старый код требует, чтобы в списке токенов магазинов были ровно два магазина (`inventory_service.py:60`), и с третьим токеном там не стартует. Без переменной API хаба выключен. Маршруты `/v1/hub/*` принимают только токен хаба, остальные маршруты его отклоняют. По одному токену хаба на каждый сайт. В хабе токены хранятся зашифрованными, как ключи маркетплейсов; сверка — за постоянное время.

## 5. Как служба считает остаток для сайта

Движения службы (знаки сверены с кодом, `inventory_engine.py:356, 367, 386`): бронь `(qd 0, rd +q)`, оплата `(−q, −q)`, снятие брони `(0, −q)`, возврат `(+q, 0)`. Сейчас `websiteAvailable = max(0, ozonFree + Σqd − Σrd)` по всей истории пула.

### 5.1 Режимы пула

Добавочная таблица `pool_source(pool_id PK, mode, mode_epoch, since_movement_id, since_snapshot_id, changed_at)`. Нет строки — режим `ozon`, поэтому старый код при откате ведёт себя как прежде.

- **`ozon`** — как сейчас. Допустим, **только пока никто не пишет остаток этого оффера в Ozon**: иначе Ozon уже учтёт продажи сайта, и служба вычтет их второй раз. Инвариант: **хаб пишет оффер в Ozon ⇒ пул в `hub`**. Это условие нарушается уже сейчас, когда владелец правит остаток в кабинете Ozon вручную: служба вычитает продажи сайта второй раз, и остаток на сайте занижается (`shopb-site/deploy/inventory/PROTOCOL.md:79-84`). Для пула `hub` правило жёсткое: **никто, включая кабинет Ozon, его остаток не пишет**, кроме хаба. Если пул вернулся в `ozon` после периода `hub`, отсчёт идёт от точки возврата: `ozonFree(замер с id > since_snapshot_id) + Σqd(id > Ws) − Σrd(id > Ws)`, где `Ws` — `W` плана, чьё число Ozon подтвердил последним. Без этой отсечки вся история вычтется второй раз.
- **`hub`** — по плану хаба (5.2).

### 5.2 План хаба и формула

План по пулу: `{poolId, modeEpoch, planSeq, W, A, ozonExposed, journalEpoch}`.
- `W` — общий курсор: наибольший номер движения службы (по всем пулам), который хаб уже учёл.
- `A` — сколько отдать сайтам; считается из журнала хаба (§6): `Free = L(W) − H(W)`, где `L(W)` — приходы и инвентаризации − списания броней сайтов (`commit`, id ≤ W) + возвраты (id ≤ W), признанные годными − отправления Ozon FBS во всех статусах, кроме отменённых. Списание брони — это и оплата банком, и ручное подтверждение перевода, QR или оплаты при получении (`shopa/src/lib/inventory-orders.ts:126-131`, `order-transitions.ts:190-191`); для товара это продажа, а выручку хаб берёт только из событий `paid` сайта (§8); `H(W) = Σrd(id ≤ W)` по пулу — живые брони сайтов. `A ≤ Free` (распределение — §6).
- `ozonExposed` — сколько выставлено в Ozon: наибольшее из последнего числа, подтверждённого чтением Ozon, и чисел в записях с неизвестным исходом. 0, если хаб этот оффер в Ozon не пишет.

Служба считает:

```
обычный режим:     websiteAvailable = max(0, A               + Σqd(id > W, вид ≠ return) − Σrd(id > W))
безопасный режим:  websiteAvailable = max(0, A − ozonExposed + Σqd(id > W, вид ≠ return) − Σrd(id > W))
```

| Событие после `W` | Изменение | Почему верно |
|---|---|---|
| бронь `q` | −q | новая бронь занимает остаток |
| оплата брони, сделанной после `W` | 0 (вместе с бронью −q) | продажа = бронь, уже вычтена |
| оплата брони, сделанной до `W` | 0 | хаб уже вычел её бронь в `A` |
| снятие брони | +q | товар снова свободен |
| возврат | 0 до следующего плана | годен ли товар к продаже, решает хаб |

Проверено на сценариях: бронь до `W` и оплата после, бронь и снятие после `W`, частичный возврат, заказ на два пула, два сайта на одном пуле, повтор операции с тем же ключом.

**Безопасный режим** включается, если хаб не присылал сигнал «жив» дольше `T` (настройка службы, по умолчанию 10 мин) или не сходится `journalId` (5.4). В нём сайт продаёт только то, что не выставлено в Ozon, поэтому двойной продажи нет при любой длине молчания хаба. Пулы, которые хаб в Ozon не пишет (`ozonExposed = 0`), продаются как обычно. **Цена для владельца:** у товара, почти весь остаток которого выставлен в Ozon (`S = Free − b`), сайт в безопасном режиме продаёт только буфер `b` — обрыв интернета или питания дома дольше `T` фактически останавливает продажу таких товаров на сайтах, пока хаб не вернётся (Ozon при этом продаёт).

### 5.3 Приём плана и сигнал «жив»

- Хаб шлёт `POST /v1/hub/heartbeat` каждый цикл, даже если планы не менялись. Время берётся по часам службы, а не по `issuedAt`: у Pi нет часов реального времени.
- План принимается, если: `modeEpoch` равен текущему; `planSeq` больше действующего; `W` не меньше действующего; `W ≤ max(movement.id)`; `journalEpoch` совпадает. Тот же `planSeq` с тем же хэшем — ответ 200 (повтор после таймаута).
- Топология отдаёт по каждому пулу действующие `planSeq`, `W`, `modeEpoch`: хаб, восстановленный из старой копии, продолжает нумерацию от них, а не отвергается навсегда.

### 5.4 Журнал для хаба

- `W` — общий курсор по `movement.id`. Номер выдаётся под блокировкой записи (`BEGIN IMMEDIATE`), читатель видит только зафиксированное, поэтому курсор строк не пропускает. Дыры в номерах (откаченные транзакции) — не потеря.
- **Служба сейчас теряет нужное хабу.** Вид возврата (`disposition`: отмена неотгруженного или возврат товара) и время события (`occurredAt`) проверяются, но не сохраняются (`inventory_engine.py:328-332, 390-392`); в `movement` есть только `created_at` — время записи, а очередь сайта может доставить событие с задержкой до 5 мин. Добавочная таблица `operation_meta(operation_id PK, store, order_id, kind, disposition, occurred_at)` заполняется в той же транзакции, лента событий отдаёт эти поля.
- `order_id` в службе — внутренний `Order.id` сайта (`shopa/src/lib/inventory-outbox.ts:30`), а не номер `RM…`. События заказа сайта (§8) несут его же как `inventoryOrderId`, чтобы хаб сшил движение товара с деньгами.
- **Идентификатор журнала `journalId`** — UUID в добавочной таблице `journal_meta`; новый при `init-new` и после **любого** восстановления базы из копии (копия службы снимается раз в сутки — `shopb-site/deploy/backup/stores-offsite-once.py`). Без него после восстановления новые движения получат уже прочитанные хабом номера: хаб их пропустит, а действующий план с большим `W` скроет новые брони — перепродажа. Курсор хаба — пара `(journalId, номер)`; при несовпадении хаб останавливает запись в Ozon, перечитывает журнал и топологию, служба включает безопасный режим. Служба отклоняет план с чужим `journalId` и с `W > max(movement.id)` (`PLAN_FROM_FUTURE`). То же правило — для журнала событий заказа на сайтах (§8): базу ShopA 17.11.2026 уже сливали из копии.
- Журнал неизменяем и не удаляется (режим `ozon` суммирует всю историю). `ack` хаба — только для контроля отставания.

### 5.5 Переключение режима

- **`ozon → hub` — только через физический пересчёт.** Владелец считает товар на полке. Хаб фиксирует `W0 = max(movement.id)` и открытые отправления Ozon и берёт `L0 = пересчёт − оплаченные неотгруженные заказы сайтов (id ≤ W0) − отправления Ozon, ещё не переданные курьеру`. Перед переключением хаб показывает разницу между первым `A` и тем, что сайт показывает сейчас, и ждёт подтверждения. Без пересчёта неизвестно, правил ли владелец число в кабинете Ozon, и старт может выдумать штуки или потерять их.
- Порядок: план → перевод в `hub` (ссылается на `planSeq` этого плана; служба отказывает, если план старше 60 с по её часам) → только потом запись оффера в Ozon.
- **`hub → ozon`:** хаб перестаёт писать оффер → ждёт, пока Ozon подтвердит последнее число → переводит пул с `since_snapshot_id` и `Ws` (5.1).
- **Пулы «только сайт»** (офлайн-остаток, товары без оффера Ozon) — строки `pool` с синтетическими полями, создаваемые мимо проверок `create_pool` (`inventory_engine.py:120-128`), но с соблюдением `NOT NULL`, CHECK и UNIQUE: `account_id='1'` (не равен настоящему `OZON_CLIENT_ID`), `warehouse_id='1'`, `offer_id='site:<id>'`, `scheme='fbs'`, без `baseline`, режим `hub`. **Из синхронизации Ozon исключаются только они** (`ozon_readonly.py:128-129, 144` брать пулы из нового `engine.sync_pools()`). Для товара, у которого уже есть пул Ozon, пул «только сайт» запрещён: два пула делили бы одни банки. Нужен режим того же пула; перепривязка в службе и так запрещена.
- Пулы `hub` с настоящим оффером Ozon **остаются в синхронизации**: замер нужен как контроль (5.6), для колонки «Ozon» на экране «Остатки» и для СММ — каталог СММ требует свежий `observedAt` и подтверждённое открытие пула (`shopa/src/lib/smm/inventory.ts:18-19`, `smm/catalogue.ts:39`) и иначе молча выкинет товар из постов. Статус пула `hub` от свежести замера не зависит (сейчас ошибка склада гасит все его пулы), а при брони для него не проверяется `cutoff_at` (`inventory_engine.py:348-355`).

### 5.7 Миграция службы и совместимость сайтов

- Схема расширяется только добавочными таблицами: CHECK-ограничения и неизменяемость старых таблиц не дают иначе. Файл `deploy/inventory/003_hub.sql`, тот же текст — в конец `schema.sql`: `pool_source`, `hub_plan`, `hub_plan_log` (неизменяемый, триггеры как у `movement`), `hub_ack`, `operation_meta`, `journal_meta`, `CREATE INDEX snapshot_run ON snapshot(run_id)`. Маркер миграции — существование `hub_plan` (по образцу `inventory_engine.py:73-74`), иначе `HUB_MIGRATION_REQUIRED`. Применять как 002: root, служба и таймеры остановлены, копия снята.
- **Откат.** Старый код стартует на новой базе (проверяет только версию и колонку, `inventory_engine.py:68-76`). Синтетические пулы у него уходят в отдельную группу синхронизации и падают с `OZON_ACCOUNT_MISMATCH`, не задевая настоящую, и показывают `unknown` — продажа закрыта, перепродажи нет. Пулы `hub` возвращаются к формуле Ozon: если хаб уже писал в Ozon, будет недопродажа, а не перепродажа. Действующие брони списываются, снимаются и возвращаются как раньше. Обязательный тест: старый движок открывает базу после 003.
- **Контракты сайтов.** Схема проекции у обоих сайтов не строгая — новые поля отбрасываются. Ломает только новое значение в `version`, `providerWritesEnabled`, `store`, `scheme` или `status` (`inventory-contracts.ts:7,18-19`): тогда разбор падает (`inventory-client.ts:106`), все товары показывают «Наличие уточняется», СММ получает `INVENTORY_UNAVAILABLE`, правка остатков запирается. Правило службы: **в старые перечисления новых значений не добавлять**; новое — только необязательными полями (`source`, `planAgeSeconds`, `hubSeenAt`, `safeMode`).
- **Порядок выкладки:** (1) ShopA, затем ShopB — терпимые контракты (`.catch` на перечислениях, новые необязательные поля, СММ понимает `source='hub'`, подпись синтетического оффера на экране); (2) служба: копия → стоп → 003 → старт **старого** кода, проекция совпадает → новый код без `INVENTORY_HUB_TOKEN`, проекция снова совпадает → включить токен; (3) перевод пулов в `hub` — только после этого.

### 5.6 Контроль расхождений

- Инвариант: хаб не пишет оффер — в Ozon свободно 0; пишет — не больше последнего записанного числа. Нарушение (например, владелец поправил число в кабинете Ozon) — алерт, безопасный режим пула и немедленная перезапись хабом.
- `max(0, …)` скрывает перепродажу. Служба отдаёт в топологии, если выражение ушло ниже нуля, экран «Остатки» сайта это показывает.

## 6. Хаб: распределение и запись в Ozon

- **Физический остаток своего склада ведёт журнал хаба.** Ответ на открытый вопрос `STOCK_MODULE_DESIGN.md:476`: **да, заказы сайтов отгружаются с того же склада, что FBS Ozon** (пул службы — это и есть оффер + склад FBS). В коде хаба это уже место `own` (`ledger`, «физический склад, с которого уходят поставки и заказы сайтов» — `src/lib/stock/places.ts:44-49`). Отсюда:
  - склад FBS = `own`; продажи сайтов и FBS — документы расхода с `own`, возвраты — `return_in` на `own`;
  - `ozon_fbs` остаётся `external` (`places.ts:71-75`) — это контроль числа, выставленного в Ozon, и в итог денег в товаре не входит;
  - `site_shopb` и `site_shopa` — каналы, а не места хранения: сейчас они `ledger` (`places.ts:99-112`), и итог «свой склад + Ozon FBS + сайты» в `stock.balances` (`STOCK_MODULE_DESIGN.md:374`) посчитал бы одну полку трижды.
- **Догон после простоя.** Документы датируются временем события. Если период уже закрыт (`assertPeriodOpen`, `src/lib/stock/posting.ts:514`), хаб проводит корректирующий документ текущей датой со ссылкой на исходное событие, а не падает.
- **Расход товара — только из двух источников:** продажи сайтов — из журнала службы (§5.4); продажи FBS Ozon — из отправлений `POST /v4/posting/fbs/list` с ключом по номеру отправления, во всех статусах, кроме отменённых. Отчёт о реализации и события заказов сайтов (§8) — только для денег. Это заменяет в `STOCK_MODULE_DESIGN.md` правило «продажа на Ozon — движений нет, себестоимость по реализации» (`:329`) для FBS-склада и «продажа с сайта — документ по выгрузке заказов» (`:331`). Склад хаба в первой версии броней не ведёт (`:431`) — здесь брони берутся из журнала службы (`H` в §5.2).
- Хаб сейчас ходит в отключённый `/v3/posting/fbs/list` (`src/lib/marketplaces/ozon/endpoints.ts:40`; v3 отключён 31.08.2026) — перевод на v4 обязателен до любой записи остатков.
- **Отправления:** перечитывать непосредственно перед каждой записью в Ozon. Статусы, в которых Ozon резервирует товар, документированы не все — поэтому считается всё, кроме отменённых. Родитель в `cancelled_from_split_pending` держит своё количество, пока не появятся дочерние отправления.
- **Инвентаризация:** на полке лежит `L + оплаченные неотгруженные заказы сайтов + отправления Ozon, ещё не переданные курьеру`. Если сравнивать пересчёт с голым `L`, выравнивание испортит журнал.
- **Распределение.** `Free = L − H` на физический товар; несколько пулов одного товара (фасовки, наборы «3 банки», два оффера) делят его с кратностью `k_p`: `Σ k_p·A_p ≤ Free`, `Σ k_p·S_p ≤ Free − b`.
  - Выше порога `K` — единый остаток: сайт видит `Free`, в Ozon пишется `S = Free − b` (`b` — буфер). Перепродажа ограничена одним циклом: не больше меньшего из продаж сайта и продаж Ozon за цикл.
  - При `Free ≤ K` — раздел без пересечения: `S + A ≤ Free` (кому сколько — настройка). Буфер в одну сторону от двойной продажи на последних штуках не спасает: сайт продаёт мгновенно, а хаб узнаёт о продаже Ozon с задержкой.
  - Если в Ozon выставлено больше целевого (запись не прошла, `ozonExposed > S`), сайт получает меньше на разницу: `A ≤ Free − max(0, ozonExposed − S)`.
- **Запись в Ozon** `POST /v2/products/stocks`:
  - значение абсолютное, «без учёта зарезервированных» — свой резерв Ozon держит отдельно; записи «прибавить/убавить» и условной записи нет;
  - до 100 пар «товар–склад» в запросе, до 80 запросов в минуту, одну пару — не чаще раза в 30 с; ошибки — по каждой позиции в `result[]`;
  - очередь записи в базе хаба: желаемое, отправлено, подтверждено чтением, код ошибки; слать изменения, а при расхождении с замером Ozon — переписывать сразу;
  - срок действия ключа виден в `POST /v1/roles` (`expires_at`) — предупреждать заранее;
  - роли ключа проверять `POST /v1/roles` (выводить только имена ролей); ключ на VPS — «только чтение», у хаба нужен свой ключ с правом записи остатков и чтения отправлений FBS;
  - формат запроса закрепить тестом по примеру из документации Ozon; каждый отказ — в журнал с кодом Ozon, без секретов; блокирующий отказ — алерт в Telegram;
  - первая запись — канарейка на одном товаре по согласию владельца.
- **Переключение пула** — §5.5 (через пересчёт, в строгом порядке).

## 7. Хаб недоступен

- Сайты продают по последнему плану. Пулы «только сайт» безопасны: служба вычитает каждую продажу сама.
- Через `T` без сигнала «жив» пулы, выставленные в Ozon, переходят в безопасный режим (§5.2): сайт продаёт только то, что не выставлено в Ozon, Ozon продаёт своё. Двойной продажи нет, витрина не гаснет целиком.
- Хаб догоняет по курсору, повтор безопасен (ключ — номер движения); журнал не удаляется.
- Видимость: служба отдаёт возраст сигнала «жив», возраст плана по каждому пулу и флаг безопасного режима; экран «Остатки» сайта показывает «хаб не на связи N мин». Алерт в Telegram, если хаб молчит дольше `T`, ставится в `shopa/scripts/inventory-dispatch.ts`: таймер раз в 30 с, доступ к службе на localhost и Telegram через прокси сайта уже есть (в самой службе Telegram нет, cron `customer-jobs` на VPS не установлен).
- **Брони без срока.** В службе брони не истекают. В режиме `hub` неоплаченный заказ занимает товар и на сайте, и в Ozon (уменьшает `S`): несколько брошенных оформлений перекрывают продажи на Ozon. Сайтам нужен срок брони (например, 2 ч) со снятием после проверки у банка (GetState / getPayment: не оплачено, ссылка отменена); оплата после снятия брони уходит на ручную проверку (`review`), как уже сделано в `shopa/src/lib/payment-attempts.ts`.
- Раз хаб — голова, его простой теперь влияет на продажи. Требования к доступности Pi — §11 и этап 0 `HUB_PLAN.md`.

## 8. Заказы и деньги сайтов → журнал хаба

**Чего у сайта сейчас нет** (ShopA, `prisma/schema.prisma`): даты оплаты, отмены и возврата у заказа (есть только `createdAt`, `updatedAt`, `firstShippedAt`); комиссии эквайринга (ЮKassa отдаёт `income_amount`, Т-Банк в GetState — нет); фактической стоимости доставки СДЭК для продавца (`deliveryCost` — цена для покупателя); готовой выгрузки заказов.

**Что добавляет сайт:**
- Добавочная таблица неизменяемых событий заказа: `id` (растущий), `orderNumber`, `inventoryOrderId` (= `Order.id`, ключ заказа в службе склада), `type` (`paid`, `refunded`, `cancelled`, `shipped`, `delivered`, `returned`), `ordinal` (номер события этого типа в заказе), `amountKopecks`, `occurredAt` (UTC), `payload`, `estimated`. Уникальность `(orderNumber, type, ordinal)`. Событие пишется **в той же транзакции**, что и переход статуса или оплаты.
- **Деньги двигают только два типа:** `paid` (+) и `refunded` (−). У `cancelled`, `shipped`, `delivered`, `returned` сумма 0 — это факты о статусе; движение товара хаб берёт только из журнала службы. Иначе одна отмена могла бы провестись дважды.
- Состав `paid`: позиции (ключ варианта `productId:variantId`, `-` без варианта; артикул и название на момент заказа; штуки; цена за штуку; сумма строки после разнесения скидок до копейки), скидки (промокод, купон, бонусы, скидка первого заказа), доставка с покупателя, итог, провайдер и способ оплаты, комиссия эквайринга, если известна. Деньги — целые копейки.
- Состав `refunded`: строки возврата или поле `scope` (`items` / `delivery`), идентификатор возврата у провайдера. Возврат, сделанный прямо в кабинете банка, события на сайте не создаёт — нужна ежедневная сверка возвратов с банком.
- Старые заказы — дозаполнением, только тем, у которых событий ещё нет (иначе заказ, оплаченный между созданием таблицы и дозаполнением, получит два `paid`). Суммы — факт; дата — из лучшего источника (для списаний, снятий и возвратов `InventoryEvent.occurredAt` точнее `PaymentAttempt.updatedAt`), с пометкой `dateEstimated`. В архив удалённые заказы (`deletedAt`) тоже выгружаются: деньги по ним были.
- **Без персональных данных:** ни имени, ни телефона, ни почты, ни адреса, ни комментария. Для повторных покупок — по желанию псевдоним покупателя (HMAC от id).
- Выгрузка `GET /api/hub/v1/order-events?journal=<id>&after=<n>&limit=500` → `{journalId, events, nextAfter, hasMore}`; токен хаба; `force-dynamic`; формат закреплён тестом в репозитории сайта; страж маршрутов (`src/__tests__/harness/route-guards.test.ts`, сейчас только `/api/admin`) расширить на `/api/hub`. У журнала сайта свой `journalId` (§5.4). Курсор по `id` корректен, пока сайты на SQLite (один писатель); при переходе на Postgres нужен курсор в порядке фиксации.

**Где на сайте ShopA рождаются события** (каждая точка — внутри своей `$transaction`, событие пишется в неё же):

| Переход | Где | Замечание |
|---|---|---|
| Оплата банком | `src/lib/order-stock.ts:123-133` (из `payment-attempts.ts:247`) | одна точка |
| Ручная оплата: перевод, QR, наличные, при получении | `src/lib/order-transitions.ts:184-189` через PATCH `api/admin/orders/[id]/route.ts:134` | для онлайн-методов запрещена |
| Возврат денег | `src/lib/payment-attempts.ts:280-292` | сумма в базе накопительная — событию нужна разница с `refundedAmount`, перечитанным в транзакции |
| Отмена | `order-transitions.ts:184-186`; прежние заказы `:115`; без общего склада `:208` | |
| Отгрузка и доставка | только PATCH, `order-transitions.ts:193` | СДЭК и доставка Ozon статус не меняют |
| Возврат товара | `src/lib/inventory-orders.ts:157-165` | статус заказа не меняется |

Где событие легко потерять: «доставлен» слит с «отправлен» в одно действие; частичный возврат Т-Банка уходит на ручную проверку без суммы (`payment-attempts.ts:210`); возврат дублирующего платежа выходит раньше записи (`:288`); деньги, ушедшие на проверку, не дают `paid` (`:235`, `:257`) — событие появится при закрытии проверки; доплата по ручной ссылке идёт мимо сайта (`api/admin/orders/[id]/payment-link/route.ts:113`).

**Дата оплаты и комиссия.** ЮKassa: комиссия = `amount − income_amount`, дата — `captured_at`; оба поля сейчас не сохраняются (`income_amount` объявлено в `src/lib/yookassa.ts:94`) — сохранять с контрактным тестом по примеру из документации. Т-Банк: ни комиссии, ни даты в ответе нет — дата = `occurredAt` подтверждённого перехода, комиссия — только из банковской выписки (раздел cashflow хаба). ShopB: платёжных попыток в базе нет, переходы — `src/app/api/admin/orders/[id]/route.ts:111-114` и `payment-state.ts:44`; дизайн событий у него свой, по тем же правилам.

**Что делает хаб** (`docs/METRICS_LAYER_DESIGN.md`): `channel='site'`, `scope_key` = `shopa`/`shopb`, `source_kind='site_order'`.
- **Ключ — событие, а не заказ:** `source_ref = <код сайта>:<orderNumber>:<type>:<ordinal>`, `source_part = item:<j> | delivery | acquiring`, номер заказа — в `posting_number`. У одного `source_ref` одна дата, поэтому сборка месяца, которая удаляет прежние проводки по набору `source_ref` независимо от даты (`METRICS_LAYER_DESIGN.md:181`), не сотрёт октябрьскую оплату при сборке ноябрьского возврата. Ключ строится из естественных полей события, поэтому восстановление журнала сайта (новый `journalId`, новые номера) выручку не задваивает.
- `paid` → `revenue` по позициям; `refunded` → `returns`; комиссия → `acquiring` **только фактом** (ЮKassa или выписка). Журнал не оценивает (`METRICS_LAYER_DESIGN.md:9`): оценка комиссии по тарифу, если нужна, — в отдельной книге `est` вне прибыли.
- Фактическая доставка СДЭК → `logistics` позже, из API СДЭК. Доставка, оплаченная покупателем, — предложение: отдельная статья `delivery_income` в группе продаж (решение хаба).

8. Офлайн-остатки: хаб публикует планы для пулов «только сайт» и для пулов с нулём на Ozon (через пересчёт, §5.5) — это и есть «ручной остаток» владельца.
9. Запись в Ozon: канарейка на одном товаре (§6), затем по товарам.

Шаги 6–9 требуют живого склада хаба, отправлений FBS v4 и постоянного исполнителя на Pi — это расходится с порядком этапов `HUB_PLAN.md:143`, где сайты и остатки идут последними. Решение о порядке — за владельцем (§12).

## 12. Открытые решения владельца

1. **Ручной остаток до хаба.** Хаб на паузе, а этап «сайты и остатки» в его плане последний. Нужен ли ручной остаток раньше — временный пульт с правами хаба (публикует планы тем же API, выключается при подключении хаба), — или ждать хаб.
2. **Порядок этапов хаба:** оставить сайты и остатки последними или поднять их раньше (§11).
3. Порог `T` безопасного режима (по умолчанию 10 мин), буфер `b` и порог раздела `K` (§6).
4. Дата выручки сайта — день оплаты по Москве (рекомендация); доставка, оплаченная покупателем, — статья `delivery_income` (рекомендация).
5. Наборы: собираются ли «3 банки» из одиночных банок (§9).
