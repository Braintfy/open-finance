# AI Environment Blueprint — как построить «память и правила» для ИИ в любом проекте

> **Что это:** самодостаточная инструкция + промпт. Скормите этот файл целиком любому ИИ
> (ChatGPT/GPT, Claude, Cursor, Claude Code, Codex, Gemini — что угодно), и он либо
> **автоматически настроит** такое окружение в вашем проекте, либо **пошагово проведёт** вас
> через настройку — в зависимости от того, есть ли у него доступ к файлам.
>
> **Для человека:** можно просто читать как обычную статью — Части 1–8 объясняют, что это
> за система и почему она работает. Новичку достаточно Уровня 1 (30 минут).

```

в его проекте систему «внешней памяти и правил» для работы с ИИ-ассистентами.
Файл целиком — твоя база знаний: философия (Часть 1), анатомия (Часть 2),

ПРОТОКОЛ:

## Часть 1. Что это и зачем (5 минут чтения)

### Проблема

Каждая новая сессия с ИИ начинается с нуля. ИИ не помнит:

- какие решения вы приняли вчера и почему;
- на какие грабли уже наступали (и наступает на них снова);
- правила проекта («у нас только pnpm», «эту таблицу не трогать»);
- что вообще за проект и где что лежит.

Результат: первые 20 минут каждой сессии уходят на пересказ контекста, ИИ
делает то, что вы уже запретили неделю назад, и качество работы — лотерея.

### Решение

Превратить проект в **самодокументирующуюся систему для ИИ**: набор небольших
markdown-файлов, которые ИИ читает в начале сессии и обновляет в конце.
Это работает в любом инструменте, потому что markdown читают все.

Система держится на четырёх китах:

| Кит | Что это | Зачем |
|---|---|---|
| **Bootstrap** | 2–3 файла, которые ИИ читает в начале каждой сессии за ~30 секунд | Мгновенный «прогрев»: ИИ знает проект, правила и текущее состояние |
| **Память** | Слои: текущее состояние / журнал граблей / история релизов / архив | Знания не теряются между сессиями и не разбухают в одном файле |
| **Правила** | Жёсткие запреты + доменные правила, привязанные к папкам кода | ИИ не делает опасного и соблюдает конвенции без напоминаний |
| **Ритуалы** | Фиксированные процедуры: «начало сессии», «конец сессии», «новая фича» | Каждая сессия оставляет систему в порядке для следующей |

### Главный принцип — экономия контекста

У ИИ ограниченное «окно внимания». Если вывалить на него 100 страниц
документации — он утонет. Поэтому всё окружение строится по правилу:

> **На старте — минимум (~8–9К токенов: карта + состояние + свежие коммиты).
> Всё остальное — по запросу, через таблицу маршрутизации «тип задачи → что читать».**

Это же правило защищает от деградации: каждый файл имеет бюджет размера, а
устаревшее уезжает в архив, а не копится.

## Часть 2. Анатомия окружения

Так выглядит полная (Уровень 3) структура. Звёздочками отмечен минимум (Уровень 1):

```
проект/
├── START.md           ★ карта проекта: что это, жёсткие правила, структура,
│                        таблица «тип задачи → какие файлы читать»
├── MEMORY.md          ★ текущее состояние: ключевые файлы, инварианты,
│                        активные грабли (компактно, ~5К токенов)
├── AGENTS.md          ★ универсальная инструкция для любого ИИ-агента
│                        (де-факто стандарт, его ищут многие инструменты)
├── CLAUDE.md            то же для Claude Code (может просто ссылаться на AGENTS.md)
├── LEARNING_LOG.md      append-only журнал граблей (пишется в момент обнаружения)
├── CHANGELOG.md         история релизов; первый заголовок [X.Y.Z] = текущая версия
├── docs/
│   └── memory-archive/  устаревшие разделы MEMORY.md (читаются только по запросу)
├── .cursor/rules/       (если Cursor) доменные правила, авто-подключаемые по папкам
│   ├── project-context.mdc   alwaysApply: компактный «всегда включённый минимум»
│   └── <домен>.mdc           правила конкретной подсистемы (по globs)
└── .claude/             (если Claude Code) обвязка процедур
    ├── skills/<имя>/SKILL.md   пошаговые процедуры («новая фича», «конец сессии»)
    ├── agents/<имя>.md         роли-сабагенты (ревьюер, доменный разработчик)
    └── settings.json           права: что ИИ можно без вопросов / спрашивать / нельзя
```

### 2.1 Bootstrap — три шага начала сессии

Пользователь пишет фразу-триггер: **«загрузи контекст \<имя проекта\>»**. ИИ выполняет ровно три шага:

1. Читает `START.md` — карта проекта, правила, маршрутизация (~3К токенов).
2. Читает `MEMORY.md` — текущее состояние и активные грабли (~5К токенов).
3. Выполняет `git log --oneline -20` — что менялось в последнее время (~0.5К).

После этого ИИ готов к задаче любой сложности. Дальше он читает **только то,
что относится к задаче** — по таблице маршрутизации из `START.md`:

```markdown
| Тип задачи | Что читать |
|---|---|
| Платёжный модуль | src/payments/*, docs/PAYMENTS.md |
| Схема БД | src/db/schema/*, после изменений дать команду миграции |
| История релизов | git log -30, НЕ весь CHANGELOG.md |
```

### 2.2 Память — четыре слоя с маршрутизацией

Ключевая идея: **разные типы знаний живут в разных местах**, и есть явные
правила, куда писать и где искать:

| Что | Куда писать | Когда |
|---|---|---|
| Новая грабля/инсайт | `LEARNING_LOG.md` (append-only, только добавлять) | в момент обнаружения |
| Инвариант, ключевой файл, активная грабля | `MEMORY.md` | в конце сессии |
| Релиз | `CHANGELOG.md` | в конце сессии |
| Устаревшие разделы MEMORY | `docs/memory-archive/` | при чистке MEMORY |

| Вопрос | Где искать |
|---|---|
| Текущее состояние, правила, грабли | `MEMORY.md` |
| Что менялось недавно | `git log --oneline -20` |
| Детали конкретного релиза | конкретный раздел `CHANGELOG.md` (не весь файл) |
| Старая история («почему отказались от X») | `docs/memory-archive/` |
| Код | поиск по коду, НЕ память |

**Бюджеты размера (критично!):** `MEMORY.md` ≈ 400–450 строк максимум.
Реальный случай: файл распух до 908 строк и съедал 25% контекста ИИ на каждом
старте. Лекарство — при каждом обновлении критически смотреть, что устарело,
и уносить в архив.

### 2.3 Правила — два уровня

**Уровень 1 — жёсткие запреты (guardrails).** Короткий список «НЕ делать
НИКОГДА» в каждом корневом файле-инструкции. Типичные примеры:

- НЕ выполнять `git add/commit/push` — давать команды пользователю.
- НЕ запускать миграции БД — давать команды.
- НЕ трогать `.env`, секреты, ключи.
- НЕ использовать \<запрещённая технология\> — только \<выбранная\> (напр. «не npm — только pnpm»).
- Новые файлы начинать с комментария `// PURPOSE: ...` (одна строка — что это).

**Уровень 2 — доменные правила.** Правила конкретной подсистемы («как у нас
устроены блоки UI», «как писать запросы к БД»). Живут в отдельных файлах,
подключаемых только когда ИИ работает с соответствующими папками
(в Cursor — автоматически через globs, в остальных — через таблицу маршрутизации).

**Анти-дрейф — самое важное правило про правила:** каждое правило живёт ровно
в **одном** файле, остальные файлы на него **ссылаются**, а не копируют. Иначе
копии разъезжаются, и ИИ получает противоречивые инструкции.

### 2.4 Версия — без хардкода

Текущая версия проекта = первый заголовок `## [X.Y.Z]` в `CHANGELOG.md`.
Её НЕ хардкодят ни в какие другие доки (они мгновенно устаревают). Бамп:
MINOR — новая фича/модуль, PATCH — фиксы.

### 2.5 Ритуал конца сессии

Пользователь пишет «заверши сессию», ИИ выполняет фиксированную процедуру:

1. **Верификация** — сборка/тесты должны быть зелёными (например `npm run build`);
   для значимых изменений — ревью-проход по диффу свежим чатом (см. Часть 7.3).
2. **CHANGELOG.md** — запись релиза: `## [X.Y.Z] - дата`, разделы
   Added/Changed/Fixed/Removed; для Fixed обязательно «Причина: … Фикс: …».
3. **MEMORY.md** — обновить, если изменились ключевые файлы/инварианты/грабли;
   заодно вынести устаревшее в архив.
4. **LEARNING_LOG.md** — записать новые грабли (если были).
5. **Git-команды пользователю** (если git запрещён ИИ):
   `git add -A && git commit -m "feat(scope): описание (vX.Y.Z)" && git push`.

Цель ритуала: **следующая сессия за 30 секунд понимает состояние системы**,
без реверс-инжиниринга и расспросов.

### 2.6 Продвинутое: скилы, сабагенты, права (Уровень 3)

- **Скилы** — пошаговые процедуры в `.claude/skills/<имя>/SKILL.md` для
  повторяющихся задач («добавить новую сущность БД», «конец сессии»). В описании
  каждого — TRIGGER (когда применять) и DO NOT TRIGGER (когда нет).
- **Сабагенты** — роли в `.claude/agents/<имя>.md`: например read-only
  код-ревьюер с чек-листом инвариантов проекта, который запускают перед коммитом.
  Первое действие каждого сабагента — прочитать свой файл доменных правил.
- **Права** — `settings.json` с тремя списками: `allow` (безопасные команды
  без вопросов: typecheck, build, git log), `ask` (спросить), `deny` (запрещено:
  git commit, миграции, чтение .env). Это машинное приведение в исполнение
  жёстких правил из п. 2.3.

## Часть 3. Три уровня внедрения

### Уровень 1 — Минимум (30 минут, для всех)

Три файла + две привычки:

1. **`AGENTS.md`** — кто мы, стек, жёсткие правила, как проверять работу.
2. **`MEMORY.md`** — текущее состояние и грабли.
3. **`LEARNING_LOG.md`** — пустой журнал с шаблоном записи в шапке.

Привычки: начинать сессию с «прочитай AGENTS.md и MEMORY.md», заканчивать —
«обнови MEMORY.md и запиши грабли».

Этого достаточно, чтобы получить 70% пользы. Подходит даже для не-кодовых
проектов (тексты, исследования, дизайн).

### Уровень 2 — Стандарт (ещё ~1 час)

Добавляется:

- **`START.md`** с таблицей маршрутизации «тип задачи → что читать».
- **`CHANGELOG.md`** + ритуал конца сессии (п. 2.5) целиком.
- **Доменные правила**: `.cursor/rules/*.mdc` (если Cursor) или раздел
  в START.md (если другой инструмент).
- **`docs/memory-archive/`** и бюджеты размеров.

### Уровень 3 — Продвинутый (по мере роста проекта)

- Скилы-процедуры для повторяющихся операций.
- Сабагенты-ревьюеры (код, безопасность).
- `settings.json` с правами allow/ask/deny.
- Опционально: семантическая память через MCP-сервер (поиск «почему мы
  отказались от X» по истории решений). Это необязательный слой — система
  полноценно работает на одних markdown-файлах.

**Важно:** не стройте Уровень 3 с первого дня. Окружение должно расти вместе
с проектом, иначе вы будете обслуживать бюрократию, а не работать.

## Часть 4. Шаблоны файлов

> ИИ: подставляй реальные данные из ответов пользователя и кода проекта.
> Плейсхолдеры в `{фигурных скобках}`. Чего не знаешь — `<!-- TODO -->`, не выдумывай.

### 4.1 `AGENTS.md` (универсальный, читают все ИИ)

```markdown
# AGENTS.md — правила для AI-агентов

> Файл для ЛЮБОГО ИИ-агента, работающего с этим проектом.

## Проект

- **Имя:** {имя}
- **Что делает:** {1–2 предложения}
- **Стек:** {технологии}
- **Версия:** первый заголовок `## [X.Y.Z]` в `CHANGELOG.md` (НЕ хардкодить в доках)

## Начало сессии (триггер — «загрузи контекст {имя}»)

1. `START.md` — карта проекта и маршрутизация задач.
2. `MEMORY.md` — текущее состояние и активные грабли.
3. `git log --oneline -20` — свежие коммиты.

Дальше — только файлы, относящиеся к задаче (таблица в START.md).

## Жёсткие правила

### НЕЛЬЗЯ НИКОГДА
- {из ответов пользователя, например:}
- НЕ делать `git add/commit/push` — давать команды пользователю.
- НЕ запускать миграции БД — давать команды.
- НЕ трогать `.env`, секреты, ключи.
- НЕ использовать {запрещённое} — только {выбранное}.

### НУЖНО ВСЕГДА
- Использовать {package manager}.
- Новые файлы начинать с `// PURPOSE: ...`.
- После изменений: {команда проверки, напр. `npm run build`}.
- Новые грабли → `LEARNING_LOG.md` сразу при обнаружении.

## Конец значимой сессии (триггер — «заверши сессию»)

1. {команда проверки} — должна пройти.
2. Запись в `CHANGELOG.md` (формат — в шапке файла).
3. Обновить `MEMORY.md`, устаревшее → `docs/memory-archive/`.
4. Новые грабли → `LEARNING_LOG.md`.
5. Дать пользователю git-команды (не выполнять самому).
```

### 4.2 `START.md` (карта + маршрутизация; Уровень 2)

```markdown
# START.md — bootstrap {имя проекта}

> Первый файл ИИ в новой сессии. Остальная документация — ПО ЗАПРОСУ.

## Часть 5. Адаптеры под инструменты

Ядро (`AGENTS.md`, `START.md`, `MEMORY.md`, `LEARNING_LOG.md`, `CHANGELOG.md`) —
одно и то же везде. Различается только способ «подключения» к инструменту:

| Инструмент | Что добавить |
|---|---|
| **Cursor** | `.cursor/rules/project-context.mdc` (`alwaysApply: true`, компактный) + доменные `.mdc` с globs — Cursor сам подключит их при работе с нужными папками. |
| **Claude Code** | `CLAUDE.md` в корне (читается автоматически; может быть копией-ссылкой на AGENTS.md: «прочитай AGENTS.md, дальше — по START.md»). Уровень 3: `.claude/skills/`, `.claude/agents/`, `.claude/settings.json`. |
| **Codex / другие CLI-агенты** | Большинство автоматически читают `AGENTS.md` — ядро уже работает. |
| **ChatGPT / Claude web (без доступа к файлам)** | Создайте Project/чат с инструкциями. В инструкции проекта вставьте содержимое `AGENTS.md`. В начале сессии вставляйте актуальный `MEMORY.md` (+ при необходимости нужные файлы по таблице маршрутизации). В конце сессии просите ИИ выдать обновлённый текст `MEMORY.md`/записи журналов — и сохраняйте руками. |
| **Универсальный чат** | То же, что ChatGPT web: AGENTS.md — в системные инструкции, MEMORY.md — первым сообщением. |

**Ключевое правило мульти-инструментальности:** доменные правила живут в
**одном** месте (например `.cursor/rules/*.mdc` — это обычный markdown, его
может прочитать любой агент), остальные файлы ссылаются на них. Не плодите
копии под каждый инструмент.

## Часть 6. Принципы и антипаттерны (выстраданные грабли)

1. **Один источник правды для каждого факта.** Правило — в одном файле, версии —
   только в CHANGELOG, ссылки вместо копий. Копии всегда разъезжаются.
2. **Бюджеты размера + архив.** MEMORY.md без чистки распухает в 9 раз и съедает
   четверть контекста ИИ. При каждом обновлении спрашивайте: «что здесь устарело?»
3. **Не грузить всё на старте.** Bootstrap — 2–3 файла. CHANGELOG (тысячи строк),
   планы и архивы читаются по запросу и частями.
4. **Журнал граблей — append-only и сразу.** Записывать в момент обнаружения,
   иначе знание потеряно. Не редактировать старые записи.
5. **Запреты — машинно, где возможно.** Если инструмент поддерживает права
   (deny-списки) — дублируйте туда жёсткие правила. Текстовый запрет ИИ может
   проигнорировать, deny-список — нет.
6. **Опасные операции — командами пользователю.** git push, миграции БД, деплой:
   ИИ готовит команду, человек выполняет. Это страховка от необратимого.
7. **Не выдумывать факты в доки.** Лучше `TODO` в шаблоне, чем правдоподобная ложь,
   которую следующая сессия примет за правду.
8. **Окружение растёт с проектом.** Не стройте скилы и сабагентов на пустом
   репозитории. Сначала 3 файла, потом по мере боли.
9. **Ритуал конца сессии — несдвигаемый.** Пропустили один раз — следующая
   сессия начнётся с археологии. Цель: новая сессия понимает всё за 30 секунд.
10. **Семантическая память (MCP/векторные базы) — опциональная вишенка**, не
    фундамент. Источник правды о текущем состоянии — всегда MEMORY.md + git log.

## Часть 7. Защита от дыр и дублей (контроль качества и безопасности)

Частая жалоба на ИИ-код: «работает, но оставляет за собой дыры в безопасности
и дублирует то, что уже есть». Это не лечится одним «плагином» — это лечится
**эшелонированной обороной**: несколько дешёвых барьеров, каждый из которых
ловит свой класс проблем. Всё ниже работает в любом инструменте.

### 7.1 Почему ИИ это делает (чтобы понимать, что чиним)

- **Дыры:** ИИ оптимизирует «чтобы заработало», а не «чтобы было безопасно».
  Если в правилах не написано «каждый эндпоинт проверяет авторизацию» — он
  легко сделает эндпоинт без проверки, захардкодит ключ «временно», отключит
  валидацию ради зелёного билда.
- **Дубли:** ИИ не видит весь проект — только то, что загружено в контекст.
  Не нашёл существующую функцию → написал свою рядом. Так появляются три
  `formatDate()` и две системы уведомлений.

Оба класса проблем — следствие отсутствия контекста и проверок. Лечение ниже.

### 7.2 Эшелон 1 — Инварианты безопасности в правилах (Уровень 1, всем)

В `AGENTS.md` (раздел «Жёсткие правила») добавьте блок инвариантов
безопасности — подберите под свой проект из типового списка:

```markdown
### Безопасность (инварианты — нарушать НЕЛЬЗЯ)
- Каждый API-эндпоинт/страница проверяет авторизацию И права доступа
  (не только «залогинен», но и «имеет право на ЭТУ запись»).
- Все данные пользователя валидируются на сервере (клиентская валидация — не защита).
- Запросы к БД — только параметризованные / через ORM. Конкатенация строк в SQL запрещена.
- Секреты ТОЛЬКО в .env / секрет-хранилище. Ключ в коде «временно» = блокер.
- Никогда не ослаблять защиту ради зелёного билда: не отключать валидацию,
  auth-проверку, CORS, rate limit «чтобы заработало». Если мешает — спросить пользователя.
- Деньги/количества — серверный пересчёт; данным с клиента не доверять
  (классический «дюп» в играх и магазинах — это доверие клиентскому значению).
- В мультипользовательских системах: каждый запрос фильтруется по владельцу
  (user_id / tenant_id) — БЕЗ исключений.
```

И туда же — правило против дублей:

```markdown
### Перед созданием нового кода (анти-дубль)
- СНАЧАЛА поиск: есть ли уже похожая функция/компонент/утилита (поиск по
  имени, по смыслу, по папкам utils/lib/helpers).
- Нашёл похожее → расширь или переиспользуй. Не нашёл → создай и впиши
  в карту проекта (START.md / MEMORY.md «Ключевые файлы»).
- Новая зависимость в package.json — только если задачу нельзя решить
  уже установленными (сначала проверь, что уже стоит).
```

### 7.3 Эшелон 2 — Ревью перед каждым коммитом (Уровень 1–2, всем)

Самый эффективный барьер: **отдельный проход «свежими глазами» по диффу до
коммита**. Важно делать это НОВЫМ чатом/агентом — тот же чат, что писал код,
свои ошибки не видит (он их уже «оправдал» в процессе написания).

Готовый ревью-промпт (вставьте в новый чат вместе с диффом, или сохраните
как `.claude/agents/code-reviewer.md` по шаблону 4.8):

```markdown
Ты — строгий ревьюер. Ничего не правь — только читай дифф и репорти.
Сначала прочитай AGENTS.md (жёсткие правила) и MEMORY.md (активные грабли).

Проверь дифф по чек-листу:
1. БЕЗОПАСНОСТЬ: новые эндпоинты без проверки авторизации/прав; доверие
   данным с клиента (цены, количества, id чужих записей); конкатенация в SQL;
   секреты/ключи/токены в коде; ослабленная валидация; отключённые проверки;
   широкие CORS; отсутствие rate limit на чувствительных операциях.
2. ДУБЛИ: не создана ли функция/компонент/константа, аналог которой уже
   есть в проекте? (проверь поиском, не по памяти).
3. МУСОР: закомментированный код, console.log/print-отладка, неиспользуемые
   импорты и файлы, «временные» обходы с TODO без задачи.
4. ИНВАРИАНТЫ ПРОЕКТА: каждый пункт из «Жёстких правил» AGENTS.md.

Формат: `файл:строка — проблема — правило — как чинить`,
секции «Блокирует» / «Желательно». Если чисто — одна строка. Не выдумывай находки.
```

В инструментах со встроенным ревью используйте его как дополнительный слой:
Cursor — Bugbot/Security review, GitHub — Copilot code review, CodeRabbit и
аналоги на pull request.

### 7.4 Эшелон 3 — Машинные барьеры (Уровень 2–3)

Текстовое правило ИИ может проигнорировать — автоматика нет:

| Барьер | Что ловит | Чем |
|---|---|---|
| Типы + линтер + сборка после каждой правки | сломанный/недописанный код | `tsc`, eslint, `build` — внести в ритуал «после изменений» |
| Секрет-сканер на pre-commit | ключи и пароли в коммите | gitleaks / trufflehog / detect-secrets |
| Аудит зависимостей | уязвимые пакеты, которые ИИ поставил не глядя | `npm audit` / `pnpm audit` / dependabot |
| Поиск дублей | копипасту между файлами | jscpd (порог ~15 строк) — гонять перед релизом |
| Deny-списки прав агента | запрещённые команды (push, миграции, чтение .env) | шаблон 4.9, если инструмент поддерживает |
| Smoke-тесты критичных модулей | регрессии в деньгах/правах/расчётах | простые скрипты `scripts/test-*.ts`, запуск в ритуале конца сессии |

Минимальный pre-commit хук (git, работает везде):

```bash
#!/bin/sh
# .git/hooks/pre-commit — не пускать секреты в коммит
if git diff --cached | grep -nE '(sk-[A-Za-z0-9]{20,}|ghp_[A-Za-z0-9]{30,}|AKIA[0-9A-Z]{16}|-----BEGIN.*PRIVATE KEY|api[_-]?key\s*[:=]\s*["'"'"'][^"'"'"']{8,})'; then
  echo "BLOCKED: похоже на секрет в диффе. Убери его или используй .env."
  exit 1
fi
```

### 7.5 Эшелон 4 — Замыкание петли через память

Каждая найденная дыра или дубль — это не только фикс, но и **запись**:

1. Грабля → `LEARNING_LOG.md` (в момент обнаружения).
2. Если класс проблемы может повториться → новый инвариант в «Жёсткие правила»
   или в чек-лист ревьюера. Пример: нашли эндпоинт без проверки владельца →
   в чек-лист навсегда добавляется пункт «проверка прав на ЭТУ запись».
3. Перед релизом — отдельный security-проход по диффу с фокусом ТОЛЬКО на
   безопасность (тот же промпт 7.3, но только пункт 1, зато въедливо).

Так система самоулучшается: каждая дыра закрывает целый класс будущих дыр.

### 7.6 Что добавить в ритуалы

- **В ритуал «после изменений»:** типы + сборка зелёные → ревью-проход (7.3)
  → только потом git-команды пользователю.
- **В ритуал конца сессии:** перед выдачей git-команд глазами пройти
  `git diff` на секреты и «временные» обходы.
- **В bootstrap:** ИИ читает инварианты безопасности вместе с остальными
  жёсткими правилами — они в том же AGENTS.md, ничего отдельно грузить не надо.

## Часть 8. Чек-лист готовности

- [ ] `AGENTS.md` существует: идентичность + жёсткие правила + bootstrap + ритуал.
- [ ] `MEMORY.md` существует, заполнено текущее состояние, указан бюджет размера.
- [ ] `LEARNING_LOG.md` существует с шаблоном записи в шапке.
- [ ] (Ур. 2) `START.md` с таблицей маршрутизации «задача → файлы».
- [ ] (Ур. 2) `CHANGELOG.md` с первой записью и форматом в шапке.
- [ ] (Ур. 2) Доменные правила для 1–3 главных подсистем.
- [ ] (Ур. 3) Права allow/ask/deny, если инструмент поддерживает.
- [ ] Жёсткие запреты пользователя попали и в AGENTS.md, и в deny-списки.
- [ ] Инварианты безопасности и правило «поиск перед созданием» — в AGENTS.md (Часть 7.2).
- [ ] Ревью-промпт сохранён (отдельный файл-агент или сниппет) и встроен
      в ритуал «после изменений» (Часть 7.3).
- [ ] (Ур. 2+) Хотя бы один машинный барьер: секрет-сканер на pre-commit
      или deny-списки (Часть 7.4).
- [ ] Проверка: новый чат, фраза «загрузи контекст {имя}» → ИИ читает 3 файла
      и корректно отвечает «что за проект и что мне нельзя».
- [ ] Проверка: фраза «заверши сессию» → ИИ выполняет ритуал из 5 шагов.
