# HUB_PLAN.md — приватный хаб продавца: цель, карта, архитектура, этапы

> **Канон с 2026-11-17.** Заменяет `docs/ROADMAP_V2.md` как ответ на вопрос «куда идём и что делать дальше».
> Основан на трёх разведках этого дня: аудит расчётов аналитики, инвентаризация кода, обзор сервисов-аналогов. Факты о коде — из чтения исходников агентами, без запуска тестов и SQL; номера строк перепроверять перед правкой.
> Роли исполнения — `.claude/ORCHESTRATION.md`. Сервер — `docs/SERVER.md`.

## 1. Цель

**Свой защищённый хаб на Raspberry Pi**, в котором один продавец видит и ведёт весь бизнес: Ozon, Wildberries, продажи с сайтов, юнит-экономика, налоги, остатки. Доступ — отовсюду, но не из открытого интернета.

Что это меняет относительно прежнего курса («публичный AI-first SaaS»):

| Было | Стало |
|---|---|
| много арендаторов, регистрация, тарифы, биллинг | один владелец, вход по паролю, регистрации нет |
| AI — главный интерфейс | AI — необязательный помощник поверх готовых цифр |
| «каждая страница — конструктор из блоков» | готовые разделы с фиксированной структурой; конструктор остаётся только на сводной странице |
| десктоп (Tauri), мобильное приложение | не делаем; мобильный доступ — тот же сайт через защищённый канал |
| публичный запуск, 152-ФЗ, капча, оферта | снято |

Критерий успеха: решения о ценах, закупках и поставках принимаются по цифрам хаба, и эти цифры сходятся с выплатами маркетплейсов и банком.

## 3. Что не так с аналитикой сейчас

Тарифы и калькуляторы уже новые. Устарела **аналитика факта** — она не доросла до модели, которую калькуляторы считают для плана.

1. **«Прибыль» = выручка − себестоимость.** Комиссия, логистика, хранение, реклама, возвраты и налог не вычитаются нигде: ни в роутах, ни в блоках, ни в сводке для AI.
2. **Отчёт о реализации никто не читает.** `ozon_realization` синкается с v0.54.0, но потребителей у таблицы нет; `ozon_transactions` используется только как запасная оценка рекламы. Фактические удержания лежат в базе неиспользованными.
3. **Себестоимость — текущая, а не на дату продажи.** Берётся `unit_products.cost_kopecks`; складская средняя (`costAtDate`) в аналитику не подключена, режим `cost_source='inventory'` по умолчанию выключен.
4. **Одна метрика — разные формулы.** Выручка: «заказано» из `ozon_analytics_daily` в KPI и таблице, «доставлено» из `ozon_orders` в ABC. Штуки: в роуте из заказов, в источнике привязок из `delivered_units` (без Premium Plus там ноль → нулевая себестоимость). Выкуп: в одном месте взвешенный, в двух — среднее процентов. ДРР: в KPI к общей выручке, в кампаниях — к рекламным заказам.
5. **Подписи врут:** «заказы» в KPI — это штуки, средний чек и CPO делятся на штуки.
6. **Реклама по строкам не сходится с итогом**, возможен двойной счёт CPC и CPO (не проверено).
7. **Границы суток** — четыре несогласованных места (этап A2 прежнего роадмапа): 3,9% заказов попадают не в свой день.

Корень один: каждая метрика считается там, где показывается. Лечится не правкой двенадцати мест, а одним слоем расчёта.

## 4. Решение по блочной структуре

**Решение (утверждено владельцем 2026-11-18): новые разделы — обычные страницы; конструктор остаётся только для сводной.**

Почему не продолжать на блоках:
- конструктор — 54 тыс. строк и главный источник «граблей» в `MEMORY.md` (порядок хуков, RSC-границы, копейки в паблишере, привязки между блоками);
- богатые возможности (карта связей, `@связать`, импорт-экспорт каждого блока, AI на блок, оформление) оплачиваются сложностью каждого нового блока, а владельцу нужны верные цифры в предсказуемом месте;
- разнобой формул из раздела 3 — прямое следствие того, что блок сам себе источник правды.

Что делаем:

| | Решение |
|---|---|
| Разделы «Аналитика», «Wildberries», «Ozon», «Сайты и остатки», «Налоги» | фиксированные страницы с вкладками и таблицами. Готового образца в проекте нет — все нынешние страницы, включая склад, собраны на BlockGrid; первой обычной страницей станет «Аналитика» |
| Сводная (`/app/dashboard`) | остаётся на конструкторе: плитки-витрины поверх общего слоя метрик |
| Существующие блоки Ozon | переводятся на общий слой метрик; свои формулы из них убираются |
| Карта связей, `@связать` между страницами, маркет блоков, AI-мутации блоков | заморозить: не развивать, новые блоки под них не подстраивать |
| Таблица «Мой магазин», `custom.data`, `sheet` | оставить как есть — это личные расчётные таблицы, они работают |

Ничего из конструктора не удаляется на этом шаге: он перестаёт быть обязательным путём для новых функций.

## 5. Целевая архитектура

```
  Ozon API      WB API      сайты (экспорт)     банк (выписки)
     │            │              │                   │
     ▼            ▼              ▼                   ▼
 ┌──────────────────────────────────────────────────────────┐
 │ 1. Коннекторы   src/lib/marketplaces/{ozon,wb}, src/lib/sites │  сырьё как есть: ozon_*, wb_*, site_*
 │    чтение по расписанию (systemd-таймеры) + действия       │
 └──────────────────────────────────────────────────────────┘
                        │
 ┌──────────────────────────────────────────────────────────┐
 │ 2. Реестр товаров и сшивка каналов   (уже есть в stock)    │  один товар ↔ offer_id Ozon ↔ nmId WB ↔ SKU сайта
 │ 3. Склад и себестоимость             src/lib/stock         │  stock_moves — единственный источник остатков
 └──────────────────────────────────────────────────────────┘
                        │
 ┌──────────────────────────────────────────────────────────┐
 │ 4. Слой метрик   src/lib/metrics  (НОВЫЙ)                  │
 │    единая таблица фактов «канал × товар × день»:           │
 │    штуки, выручка, комиссия, логистика, хранение, реклама, │
 │    возвраты, прочие удержания, себестоимость, налог        │
 │    + одна функция на каждую метрику (прибыль, маржа, ДРР…) │
 └──────────────────────────────────────────────────────────┘
          │                    │                    │
   страницы разделов     плитки сводной      выгрузки / AI (только чтение)
```

Правила слоя метрик:
- каждая метрика определена **один раз**; страница, плитка и AI получают её из одного места;
- коннектор каждого канала отвечает только за перевод своего сырья в общую таблицу фактов — новый канал не требует новых формул;
- факт главнее оценки по тарифам: прибыль считается по операциям площадки на дату операции, отчёт о реализации — контрольная книга для сверки; прогноз по заказам в пути — отдельное поле, с фактом не складывается;
- себестоимость — со склада на дату продажи; где её нет — строка помечается, а не считается нулём;
- все окна — полуоткрытый интервал по московскому календарю.

Что сохраняется без изменений: Next.js + Postgres + Drizzle, один процесс под systemd, фон на таймерах (без Redis и очередей), шифрование ключей API в базе, дисциплина `tenant_id` в запросах (она дешёвая и уже проверяется гейтом), жёсткие правила проекта.

**Доступ «отовсюду».** Наружу сервер не открываем. Вариант по умолчанию — частная сеть поверх интернета (WireGuard до своего VPS либо Tailscale): телефон и ноутбук видят хаб как в домашней сети, из интернета он невидим. Сайты хаб опрашивает сам, исходящими запросами — входящих соединений к нему нет.

## 6. Что забираем у аналогов

Изучены TrueStats и Yoolip напрямую; SelSup частично; остальные — по обзорам. Официальная документация WB API агенту не открылась — раздел 7.2 сверить с `dev.wildberries.ru`.

**Обязательный минимум (есть почти у всех):** автосинк по ключу; сводка с выручкой, заказами, выкупами, возвратами и сравнением периодов; чистая прибыль и маржа по артикулу со всеми удержаниями; налоги; реклама с ДРР и CPO; P&L и движение денег с выплатами; остатки, дни запаса и план поставок; фильтры по магазину, бренду, артикулу; свои колонки и экспорт.

**Берём:**

| Идея | Откуда | Куда у нас |
|---|---|---|
| «Рука на пульсе»: таблица артикул × день с планом/фактом, маржой, воронкой и рекламой | TrueStats | главная вкладка «Аналитики» |
| Прогноз прибыли по заказам, которые ещё едут | TrueStats | слой метрик: оценка до прихода факта |
| Тепловая карта «метрика × артикул × день» | TrueStats | вкладка «Аналитики» — быстрый поиск просадок |
| Плановая и фактическая юнитка рядом | Yoolip | калькуляторы уже есть — добавить колонку «факт» из слоя метрик |
| Упущенная выручка от дефицита в рублях + дни запаса | Yoolip | раздел «Сайты и остатки» |
| Дневник действий: изменил цену → что стало через N дней | Yoolip, TrueStats | журнал при каждом действии из хаба |
| Единый остаток по каналам с автообновлением | SelSup | этап 4 |
| Перенос карточек между каналами через общую карточку | SelSup | импорт Ozon → WB, этап 2 |
| Уведомление в Telegram об убыточном артикуле и дефиците | Маяк, Shopstat | после этапа 1 |

**Не берём:** мультикабинеты и роли сотрудников, тарифы по обороту, внешнюю аналитику ниш и конкурентов, генератор инфографики, складскую логистику со сканерами, автобиддер рекламы (вернуться после этапа 3, если понадобится).

## 7. Этапы

Порядок задан владельцем: аналитика → Wildberries → Ozon → сайты и остатки. Перед ними — нулевой этап, без которого нельзя ни деплоить, ни безопасно менять расчёты.

### Этап 0 — опора (инфраструктура)

**Решение владельца 2026-11-18: сервер ставим заново** — новый NVMe, свежая ОС, данные со старой флешки. Процедура — `docs/BACKUP_RESTORE.md`, «Основной путь: чистая установка». Начинаем, когда владелец поставит диск и ОС.

1. Старую флешку не трогать: на ней единственные экземпляры базы и секретов.
2. Свежая ОС на NVMe с SSH-ключом этого ПК, заданным при записи образа.
3. Со старой флешки забрать секреты, базу, `.cursor/rules/*.mdc` и расхождения кода с git; правила закоммитить.
4. Развернуть приложение, восстановить базу, проверить синк Ozon.
5. Бэкап-таймер, первый архив на ПК, проверка восстановлением.
6. Один пароль администратора, SSH только по ключу.

**Готово, когда:** с ПК проходит деплой, на ПК лежит проверенный архив, правила в git.

### Этап 1 — аналитика, которая сходится с деньгами

> **Дизайн этапа — `docs/METRICS_LAYER_DESIGN.md`** (журнал проводок + дневные факты; порции работ и проверки — там, раздел 10). Чистые модули (порции 1–2) можно делать до появления сервера.
>
> **Срочно при первом входе на сервер — устаревшие методы Ozon.** По справочнику в репозитории срок отключения уже прошёл у пяти методов, которыми пользуется синк: списки отправлений FBS и FBO (стейдж заказов), список финансовых операций (стейдж операций), список складов и остатки FBS. Справочник — снимок, поэтому работают ли они сейчас, неизвестно: первым делом смотреть журнал синка. Если хоть один отключён — его перевод на метод-замену идёт раньше любой новой аналитики.

1. **Слой метрик и таблица фактов** — схема, определения метрик, тесты-эталоны на каждую формулу.
2. **Ozon → факты:** удержания из отчёта о реализации и транзакций, себестоимость со склада на дату, реклама из одного источника без двойного счёта.
3. **Налоговый профиль** (режим и ставки — настройкой) и расчёт налога в факте по тем же правилам, что в калькуляторах.
4. **Границы суток** — довести до одной конвенции.
5. **Сверка:** прибыль за закрытый месяц по хабу против выплат Ozon; расхождение объяснить построчно. Это приёмочный тест этапа.
6. **Страница «Аналитика»:** вкладки «Пульс» (артикул × день), «P&L» (водопад по периодам), «Товары» (юнитка факт против плана), «Реклама», «Тепловая карта».
7. Существующие блоки Ozon перевести на слой метрик, исправить подписи.

**Готово, когда:** сверка за месяц сходится в пределах оговорённой погрешности, и одна метрика показывает одно число на всех экранах.

### Этап 2 — Wildberries

1. **Коннектор** по образцу Ozon: клиент с лимитами по категориям, ключ шифруется в базе, стейджи синка, таймер.
2. **Чтение:** карточки и цены, остатки, заказы и продажи, отчёт о реализации, удержания (логистика, хранение, приёмка, штрафы), реклама, воронка карточки.
3. **WB → таблица фактов** — после этого WB появляется в «Аналитике» без новых формул.
4. **Страница «Wildberries»:** «Сводка», «Товары», «Цены», «Остатки», «Заказы», «Финансы», «Реклама».
5. **Управление:** изменение цен и скидок, остатков FBS; каждое действие — с подтверждением и записью в дневник.
6. **Импорт товаров из Ozon:** карточка Ozon → черновик в хабе (название, описание, фото, штрихкод, габариты) → выбор предмета WB и дозаполнение обязательных характеристик → отправка в WB. Полного автомата не будет: справочники характеристик у площадок разные.

Категории WB API, которые понадобятся (сверить с официальной документацией): Content, Prices, Marketplace, Statistics, Analytics, Finance, Promotion. Токен создаётся в кабинете WB с выбором категорий и режима «только чтение / чтение и запись».

**Готово, когда:** сверка месяца WB сходится, цена и остаток меняются из хаба, один товар перенесён из Ozon в WB целиком через хаб.

### Этап 3 — Ozon как раздел управления

1. Страница «Ozon» по тому же шаблону, что WB, поверх уже существующего синка.
2. Управление: цены, остатки FBS, участие в акциях.
3. План поставок по кластерам: сколько и куда везти, дни запаса, упущенная выручка.
4. Добрать данные, которые Ozon отдаёт, а мы не берём: категории и бренды, возвраты с причинами, воронка карточки.

**Готово, когда:** ежедневная работа с Ozon идёт из хаба, а не из кабинета продавца.

### Этап 4 — сайты и единые остатки

1. **Коннектор сайтов:** на каждом сайте — закрытый экспорт заказов и остатков по ключу; хаб забирает сам.
2. **Продажи сайтов → таблица фактов** (эквайринг, доставка — как удержания).
3. **Единый остаток:** один товар — одно число на своём складе, распределённое по каналам с резервом; при продаже в одном канале остаток обновляется в остальных.
4. **Страница «Сайты и остатки»:** продажи по сайтам, остатки по местам, дни запаса, план закупки по всем каналам сразу.
5. **Налоги:** страница с базой по всем каналам, расчётом к уплате и календарём сроков.

**Готово, когда:** остаток правится в одном месте, а сводная показывает весь бизнес одной строкой P&L.

### Сквозное — уборка
