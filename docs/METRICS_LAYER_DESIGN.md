## 1. Суть

1. **Журнал `fin_entries`** — одна строка = одна сумма одной статьи из одного исходного документа канала. Журнал не оценивает и не разносит суммы *между* документами; единственное деление внутри него — сумма документа по его же товарам. Сумма журнала обязана совпадать с сырьём до копейки.
2. **Дневные факты `fin_facts_daily`** — «канал × аккаунт × товар × день × статья», собираются из журнала: разносятся суммы без товара, добавляются себестоимость и налог. **Все экраны, плитки и AI читают только эту таблицу.**
3. **Формулы `src/lib/metrics/formulas.ts`** — чистые функции над суммами статей. Каждая метрика определена один раз.

**Главное решение редакции: прибыль считается по одной книге — по операциям площадки на дату операции.** Отчёт о реализации в прибыль не входит никогда: он хранится рядом как контрольная книга и сверяется с операциями помесячно. Причина: отчёт месячный, без дней и без номеров отправлений, приходит только за закрытый месяц; любая схема «закрытый месяц из отчёта, текущий из операций» задваивает или теряет продажи, попавшие в разные месяцы в двух источниках, и ломает дневные разрезы. Это меняет прежнюю рекомендацию в `HUB_PLAN.md` («признавать по отчёту о реализации») — решение остаётся за владельцем, но признание по отчёту потребует построчного отчёта с номерами отправлений и в первую версию не входит.

## 2. Схема

Во всех таблицах `tenant_id uuid NOT NULL REFERENCES tenants(id) ON DELETE CASCADE`.

```sql
fin_entries (
  id bigserial PK, tenant_id,
  channel varchar(16) NOT NULL,          -- ozon | wb | yandex | site | hub (расходы вне каналов)
  scope_key varchar(64) NOT NULL,        -- account_id::text либо код сайта; '-' если аккаунта нет
  book varchar(8) NOT NULL,              -- ops (операции — книга прибыли) | rlz (отчёт о реализации — контроль) | ads (рекламный кабинет)
  entry_date date NOT NULL,              -- календарный день МСК
  line varchar(32) NOT NULL,             -- статья из реестра (раздел 3)
  amount_kopecks bigint NOT NULL,        -- со знаком источника в смысле P&L: доход +, расход −
  qty integer NOT NULL DEFAULT 0,        -- всегда ≥ 0; смысл задаёт статья
  item_key varchar(200) NOT NULL DEFAULT '',  -- см. правило ниже
  external_sku varchar(200),
  posting_number varchar(100),
  source_kind varchar(24) NOT NULL,      -- ozon_txn | ozon_accrual | ozon_rlz | ozon_perf | wb_report | site_order | cashflow | stock_doc
  source_ref varchar(160) NOT NULL,      -- id документа-источника
  source_part varchar(160) NOT NULL,     -- часть документа
  source_code varchar(160)               -- сырое имя типа операции или услуги
)
UNIQUE (tenant_id, channel, scope_key, source_kind, source_ref, source_part)
INDEX (tenant_id, channel, scope_key, entry_date)

fin_facts_daily (
  tenant_id, channel varchar(16), scope_key varchar(64), day date,
  item_key varchar(200) NOT NULL,
  line varchar(32) NOT NULL,
  alloc varchar(16) NOT NULL DEFAULT 'direct',   -- direct | ads_sku | by_revenue_day | by_revenue_month | tax_profit
  stock_item_id uuid,                    -- NULL = нет сшивки
  amount_kopecks bigint,                 -- NULL допустим только у статьи cogs: «неизвестно»
  qty integer NOT NULL DEFAULT 0,
  base_qty integer NOT NULL DEFAULT 0,   -- qty × qty_per_unit
  PRIMARY KEY (tenant_id, channel, scope_key, day, item_key, line, alloc)
)
INDEX (tenant_id, day), INDEX (tenant_id, stock_item_id, day)

fin_months (                             -- паспорт «канал × аккаунт × месяц»
  tenant_id, channel, scope_key, month date,
  state varchar(8) NOT NULL,             -- none | built | stale | failed
  stale_reasons jsonb, build_error text, built_at timestamptz,
  formula_version integer NOT NULL,
  inputs jsonb NOT NULL,                 -- покрытие сырья датами по каждому источнику, доля разнесённого по выручке
  totals jsonb, prev_totals jsonb,       -- { "<статья>": копейки } этой и прошлой сборки
  recon jsonb,                           -- результат сверки
  closed_at timestamptz, closed_totals jsonb, closed_drift jsonb,
  PRIMARY KEY (tenant_id, channel, scope_key, month)
)

fin_tax_months (                         -- налог считается по бизнесу, не по каналу
  tenant_id, month date,
  income_ytd_kopecks bigint, expenses_ytd_kopecks bigint, tax_ytd_kopecks bigint,
  tax_month_kopecks bigint, complete boolean NOT NULL, built_at timestamptz,
  PRIMARY KEY (tenant_id, month)
)

biz_tax_profile (
  id uuid PK, tenant_id, valid_from date NOT NULL,   -- один профиль на календарный год (раздел 6)
  mode varchar(24) NOT NULL,             -- usn_income | usn_income_minus | none
  rate_bp integer NOT NULL, min_tax_bp integer NOT NULL DEFAULT 100, vat_rate_bp integer NOT NULL DEFAULT 0,
  income_base varchar(16) NOT NULL,      -- buyer_price | with_topups
  note text, UNIQUE (tenant_id, valid_from)
)

fin_line_overrides (id uuid PK, tenant_id, channel varchar(16) NOT NULL, source_code varchar(160) NOT NULL,
                    line varchar(32) NOT NULL, note text, UNIQUE (tenant_id, channel, source_code))
fin_opex_categories (tenant_id, category_id uuid REFERENCES categories(id) ON DELETE CASCADE, PRIMARY KEY (tenant_id, category_id))
fin_settings (tenant_id, key varchar(64), value jsonb NOT NULL, PRIMARY KEY (tenant_id, key))
  -- ключи: recon_threshold_kopecks, manual_cost_fallback, sales_source.<channel>.<scope>
```

**`item_key`** — единый ключ товара в журнале и фактах:
- `offer_id` канала, если он известен;
- иначе `sku:<числовой sku>` — товар есть, но артикул продавца не найден;
- иначе `item:<stock_item_id>` — источник знает только внутренний товар (складские документы импорта);
- `''` — только суммы, у которых товара нет.

Для операций и рекламы Ozon, где есть лишь числовой `sku`, артикул ищется в порядке: `stock_item_links.external_sku` → `ozon_orders.items` по номеру отправления → `unit_products.sku`.

**Части документа (`source_part`):** `accruals`, `commission`, `svc:<i>` (i — порядковый номер услуги); у операции с несколькими товарами — `<часть>/item:<j>`. Сумма части делится по товарам пропорционально числу вхождений товара в операции (суммы позиции у Ozon нет), методом наибольших остатков. `residual` — см. раздел 9. Для отчёта о реализации и рекламы один документ даёт несколько статей, поэтому там `source_part` = код статьи (`rlz_revenue`, `ads`, `ads_bonus`…). Для отчёта о реализации `source_ref = «ГГГГ-ММ:<номер строки>»` — не `sku`: один товар приходит несколькими строками. Номера строки в таблице сейчас нет, а в ответе площадки он необязателен: в порции 3 в `ozon_realization` добавляется колонка `row_no` — порядковый номер строки в ответе, его пишет синк.

**Факты — это суммы по первичному ключу.** Несколько проводок с одним ключом (две кампании с одним товаром в один день, две доли остатка) складываются в одну строку; расшифровка до отдельных документов — через журнал.

Не материализуются: производные метрики, прогноз по заказам в пути, сравнение периодов.

## 3. Статьи

Реестр — `src/lib/metrics/lines.ts`: код, название, группа водопада, флаг `inProfit`, ожидаемый знак (для отображения и контроля; сумма всегда пишется со знаком источника, принудительно знак не ставится).

| Группа | Статьи | В прибыли |
|---|---|---|
| Продажи | `revenue`, `returns`, `mp_topup` (доплаты площадки к цене) | да |
| Удержания площадки | `commission`, `logistics`, `return_logistics`, `last_mile`, `storage`, `acquiring`, `penalties`, `other_fees` | да |
| Доходы от площадки | `compensation` | да |
| Реклама | `ads` | да |
| Свои расходы | `cogs`, `tax`, `opex` | да |
| Неразобранное | `unclassified` | да |
| Контроль (вне прибыли) | `ads_settled`, `ads_bonus`, `rlz_revenue`, `rlz_returns`, `rlz_commission`, `rlz_topup` | нет |
| Меры (вне прибыли) | `ordered`, `views`, `cart_adds` | нет |

**Прибыль = сумма статей с `inProfit`, при условии что ни одна не равна NULL.**

**Штуки.** `qty ≥ 0` всегда; смысл — по статье: у `revenue` продано, у `returns` возвращено, у `ordered` заказано. Чистые продажи в штуках = `qty(revenue) − qty(returns)`; выкуп считается по штукам.

**Классификация.** Чистая `classify(channel, sourceCode, overrides)`: словарь в коде плюс ручные правки владельца. Неизвестный код не угадывается — сумма идёт в `unclassified` с сохранённым `source_code` и появляется на экране сверки. Фильтр рекламы по подстроке, продублированный в трёх местах кода, заменяется словарём.

**Реклама.** Кабинет и удержания с баланса — два взгляда на один расход, складывать их нельзя.
- В прибыль идёт `ads` = деньги, потраченные по кампании за день (`money_spent_kopecks` из `ozon_perf_expense_daily`), `source_ref = «день:campaign_id»`. Бонусы — отдельная мера `ads_bonus` вне прибыли.
- Рекламные операции из взаиморасчётов — `ads_settled`, вне прибыли, для сверки.
- Услуги продвижения, которых нет в рекламном кабинете, — `other_fees`, в прибыли всегда.
- День с расходом по товарам, но без строки итога в кабинете, помечается в паспорте как неполный.

**Разнесение** — одна чистая функция `allocate(total, weights)`: работает с модулем суммы и возвращает части со знаком `total`; веса ≤ 0 отбрасываются; сумма частей всегда равна целому (метод наибольших остатков); при пустых весах всё остаётся в `item_key = ''`.

| Что | Как |
|---|---|
| реклама кампании за день | прямая часть (`alloc='ads_sku'`) — по расходу товаров этой кампании из `ozon_perf_sku_stats`; если расход по товарам больше итога кампании, прямая часть ужимается до итога, превышение пишется в сверку; остаток ≥ 0 — по выручке дня (`by_revenue_day`) |
| хранение, прочие удержания и штрафы без товара | по выручке месяца (`by_revenue_month`): вес — выручка пары «товар × день» за месяц, строка пишется этим днём; при пустых весах сумма остаётся в день исходной проводки с `item_key = ''`. Хранение — по остаткам, когда появится их история |

Вес «выручка» — это всегда статья `revenue` книги операций. Разнесение считается на целых единицах (день, месяц), поэтому числа не зависят от периода, открытого на экране. Доля разнесённого по выручке хранится в паспорте месяца как мера неточности товарной прибыли.

## 4. Время

- **День** — календарный день Москвы; периоды — полуинтервал `[from, toExclusive)`. Общий тип — `src/lib/metrics/period.ts`; существующий `ozon/query-period.ts` не переписывается (рабочий код, риск без пользы) — его тип периода совместим с общим.
- **Продажи, возвраты, комиссия, удержания** датируются днём операции площадки. Возврат в августе июльской продажи уменьшает август — так же, как выплату.
- **Отчёт о реализации** пишется в контрольные статьи `rlz_*` последним днём своего месяца. Проводки строятся из раздельных блоков доставки и возврата в сыром ответе, а не из колонок таблицы: в колонках возвраты уже вычтены, а выручка включает доплаты площадки.
- **Текущий месяц** ничем не отличается от закрытого: это уже начисленные операции. Признак полноты месяца — покрытие сырья датами в паспорте.
- **Прогноз** по заказам в пути — отдельная функция и отдельное поле ответа, в фактах не хранится.

## 5. Себестоимость

- `cogs` пишется в день продажи: `−qty × qty_per_unit × средняя со склада на этот день`; в день возврата — та же формула с плюсом. Одна статья, суммы складываются.
- **Сшивка** — чистая `resolveLink`, порядок: `(канал, аккаунт, item_key)` → `(канал, '-', item_key)` → то же по `external_sku`. Точное совпадение аккаунта приоритетнее. Не через `unit_products`.
- **`costSeries(events, dates[])`** — новая чистая функция: лента одного товара, один проход, результат `Map<дата, {avgCostKopecks, basis} | null>`. Обязана совпадать с `costAtDate` на каждой дате; обязательные кейсы теста — дата до первого события (`null`), лента из одних расходов (`null`), исчерпанный пул (средняя сохраняется), несколько событий в день (порядок по `seq`), дата включительно.
- **Нет сшивки или нет средней на дату → `amount_kopecks = NULL`.** Запросы отдают по `cogs` сумму известных, число и выручку строк с NULL; при ненулевом числе прибыль = `null`, рядом — «прибыль по товарам с известной себестоимостью». Ручная `unit_products.cost_kopecks` подставляется только при включённой настройке `manual_cost_fallback`, с пометкой.
- **Каналы, чьи продажи проведены складскими документами** (импорт WB и Яндекса): `revenue` и `cogs` берутся из документов продаж **и документов возвратов**, `item_key = item:<stock_item_id>`, штуки уже в базовых единицах; `resolveLink` для такого ключа не вызывается. Импорт сворачивает день в нетто (продано 10, возвращено 3 → документ на 7), поэтому возвраты и выкуп по этим каналам занижены и помечаются как нетто — до появления коннектора по API.
- **Известное искажение:** продажи Ozon склад не списывают, пул завышен, средняя неточна при меняющейся закупочной цене. Лечение — проводить продажи Ozon документами склада (порция 10); до неё себестоимость Ozon помечается оценочной.

## 6. Налог

Две разные функции в `src/lib/metrics/tax.ts`:
- `calcUnitTax(netRevenue, deductible, mode, ratePct)` — перенос существующей `calcTax` **без единого изменения** (на единицу, в рублях, минимальный налог внутри). Её импортируют оба калькулятора; дубль исчезает, тесты калькуляторов остаются зелёными.
- `calcPeriodTaxKopecks({incomeYtd, expensesYtd, profile})` — для слоя: целые копейки, ставки в базисных пунктах, округление `Math.round`, без минимального налога. «Доходы»: `max(0, incomeYtd) × ставка`. «Доходы минус расходы»: `max(0, incomeYtd − expensesYtd) × ставка`.
- `calcMinTaxKopecks({incomeYtd, profile})` — минимальный налог года: `max(0, incomeYtd) × min_tax_bp`; только для «доходы минус расходы».

Правила:
- Налог считается по бизнесу целиком, нарастающим итогом с начала года. Налог месяца = итог на конец месяца − итог на конец предыдущего; в убыточный месяц он может быть отрицательным, но итог с начала года не опускается ниже нуля. Пример («доходы минус расходы», 15 %): январь — доход 100, расходы 140 → итог 0, налог января 0; февраль — доход 200, расходы 100 → итог (300 − 240) × 15 % = 9, налог февраля 9.
- **Один профиль на календарный год**: действует профиль с самой ранней датой `valid_from` в этом году (или унаследованный с прошлого). Смена режима или ставки посреди года слоем не поддерживается — так формула остаётся однозначной.
- Минимальный налог показывается строкой «доначисление до минимального» в декабре (`max(0, минимальный − итог года)`) и прогнозом в течение года.
- Режим «ОСНО» слоем не поддерживается: налог не считается, метрики помечаются.
- Доход — сумма статей `revenue` и `returns` (возвраты отрицательны), плюс `mp_topup` при `income_base = with_topups`. Расходы — сумма расходных статей в прибыли, кроме самого налога, взятая по модулю.
- **Сборка налога — отдельная единица «бизнес × год»**: запускается после сборки каналов, пересчитывает `fin_tax_months` с самого раннего изменённого месяца до конца года и переписывает строки `tax` в фактах.
- **Строка `tax` в фактах** пишется последним днём месяца, `alloc='tax_profit'`. Положительный налог месяца разносится на товары: при «доходах» — по доходу товара, при «доходы минус расходы» — по положительной доналоговой прибыли. Отрицательный налог месяца и неразнесённый остаток пишутся одной строкой `channel='hub'`, `scope_key='-'`, `item_key=''`. Это допущение: налог — величина бизнеса, его товарная разбивка условна.
- `complete = false`, если с начала года есть месяц любого канала не в состоянии `built` либо есть строки `cogs = NULL` при режиме «доходы минус расходы».
- **Это управленческая оценка, не декларация.**

## 7. Сборка и свежесть

**Исполнитель один — `scripts/metrics-build.ts`.** В обработчиках чтения (GET) сборка запрещена.
- После ежедневного синка — отдельный юнит `of-metrics-build.service`, запускается независимо от кода выхода синка.
- Частый таймер (каждые 10 минут): собирает месяцы в состоянии `stale` и `failed`, не больше нескольких за запуск, от новых к старым.
- Кнопка «Пересчитать» — POST-роут, собирает один месяц синхронно.

**Единица — «канал × аккаунт × месяц».** В одной транзакции под `pg_advisory_xact_lock` (как в `src/lib/stock/posting.ts`):
1. построить проводки месяца из сырья;
2. удалить прежние проводки **по набору `source_ref` вставляемых документов**, независимо от их старой даты; если проводка переехала из другого месяца — пометить тот месяц `stale`;
3. удалить все прежние проводки этого месяца, которых нет в построенном плане (в том числе документ, чья дата переехала в другой месяц);
4. записать проводки, пересчитать факты месяца (кроме `tax`), обновить паспорт.

Месяцы собираются по возрастанию. Затем — сборка налога (раздел 6).

**Состояния:** `none → built` (сборка), `built → stale` (`markStale`), `stale → built` (сборка), любое `→ failed` (ошибка; прежние факты остаются, причина в `build_error`), `failed → built` (успешная сборка). Закрытие — отдельный признак `closed_at`, со `state` не связан.

**`markStale(tenant, {fromDate, channel?, reason})`** вызывают: проведение и сторно складского документа (все месяцы начиная с даты документа), изменение сшивки или `qty_per_unit`, изменение налогового профиля, ручного правила классификации, списка категорий расходов. Кроме того, сборщик сам считает устаревшим месяц, у которого `formula_version` меньше константы в коде — одна константа на слой, поднимается при любом изменении словаря, разнесения или формул.

**Покрытие сырья.** Ежедневный синк операций расширяется с 30 дней до «с первого числа позапрошлого месяца», чтобы три пересобираемых месяца были покрыты целиком. Месяц, не покрытый сырьём полностью, не пересобирается автоматически; сверка по нему не запускается.

**Закрытие месяца.** Разрешено из `built` при зелёной сверке. `closed_totals` — суммы по статьям на момент закрытия. Экраны всегда показывают живые факты; закрытые числа и строка «изменилось после закрытия: N ₽, причины» (`closed_drift`) показываются в шапке P&L и на экране сверки. Так разбивка по товарам и итог не расходятся между собой, а изменение прошлого не проходит молча.

## 8. API слоя

```
src/lib/metrics/
  lines.ts  period.ts  classify.ts  allocate.ts  tax.ts  formulas.ts  resolve-link.ts   — чистые
  build-plan.ts     чистое ядро сборки месяца: сырьё → проводки → факты
  build.ts          запись плана в БД, блокировка, паспорт
  queries.ts        getFacts, getPnl, getEntries (расшифровка), getMonthStatus
  channels/ozon/{entries-ops,entries-rlz,entries-ads}.ts
```

- `getFacts({tenantId, period, groupBy, filters})` → суммы статей; для `cogs` — сумма известных, число и выручка неизвестных.
- `getPnl({tenantId, period, compareTo?})` → водопад и метрики за период и период сравнения.
- Метрика — `{ value: number | null, complete: boolean }`; `null` нигде не превращается в ноль.

Метрики `formulas.ts` (суммы статей — со знаком, расходы отрицательны):

| Метрика | Формула | Когда `null` |
|---|---|---|
| `netRevenue` | `revenue + returns + mp_topup` | — |
| `profit` | сумма статей с `inProfit` | есть `cogs = NULL` |
| `marginPct` | `profit / netRevenue` | `profit = null` или `netRevenue ≤ 0` |
| `drrPct` | `−ads / netRevenue` | `netRevenue ≤ 0` |
| `buyoutPct` | `(qty(revenue) − qty(returns)) / qty(revenue)` | `qty(revenue) = 0` |
| `roiPct` | `profit / −cogs` | `profit = null` или `cogs = 0` |
| `feesPct` | `−(удержания площадки) / netRevenue` | `netRevenue ≤ 0` |
| `avgCheck` | `netRevenue / (qty(revenue) − qty(returns))` | знаменатель ≤ 0 |
| `unitProfit` | `profit / base_qty` чистых продаж | `profit = null` или знаменатель ≤ 0 |
- Сведение по внутреннему товару — по `stock_item_id` и `base_qty`.
- Расшифровка разнесённой строки ведёт к исходным проводкам той же статьи за тот же день или месяц.
- Блоки Ozon переводятся на слой по одному; их собственные формулы и запросы удаляются.

## 9. Сверка — приёмочный тест

1. **Журнал против сырья (0 копеек):** сумма проводок книги операций за месяц = сумма операций площадки. Если части операции не складываются в её сумму, разница пишется проводкой `residual`; **любой ненулевой `residual` — красный тест** (иначе ступень была бы тождеством).
2. **Факты против журнала (0 копеек):** по каждой статье, кроме `cogs` и `tax`, сумма фактов = сумма проводок.
3. **Операции против отчёта о реализации:** `revenue`, `returns`, `commission` против `rlz_*` за месяц. Разница объясняется переносом между месяцами; показывается строкой, в прибыль не входит.
4. **Начислено против выплаты:** входящий остаток + начислено − выплаты = исходящий остаток по балансу площадки; строки моста — реклама кабинета против удержанной, неразобранное.

Тест красный, если `Σ|unclassified|` больше 0,5 % оборота или необъяснённый остаток ступени 4 выше порога владельца (`recon_threshold_kopecks`). Экран показывает топ строк по расхождению с переходом к исходной операции.

## 11. Что проверить на живой базе

1. **Устаревшие методы Ozon.** По справочнику в репозитории дата отключения уже прошла у пяти методов, которыми пользуется синк: оба списка отправлений (стейдж заказов), список финансовых операций (стейдж операций — основа этого слоя), список складов и остатки FBS. Ещё один помечен без даты (остатки по складам). Справочник — снимок, поэтому **работают ли они сейчас, неизвестно**: проверить журнал синка первым делом. Замены в справочнике названы; для операций это `/v1/finance/accrual/{postings,types,by-day}` — начисления по товару со справочником типов, что заменит и словарь, и деление по товарам.
2. Реальный список типов операций и услуг — `SELECT DISTINCT`; словарь пишется только по нему.
3. Как записана дата операции: она пишется через `new Date(строка без зоны)` в колонку без зоны и зависит от часового пояса процесса. Проверить значения; запись исправить на явный разбор московского времени.
4. Что такое «начисление за продажу» в операции: цена покупателя или с доплатами площадки; приходят ли доплаты отдельными операциями.
5. Входит ли оплата за заказ в итог рекламного кабинета; какими типами операций удерживается реклама.
6. Есть ли у позиций операции количество или сумма в сыром ответе.
7. Баланс площадки: доступность метода, глубина, форма ответа.
8. Глубина истории операций и отчётов о реализации.
9. Доля товаров без сшивки и без себестоимости; доля сшивок со `scope_key = '-'`.
10. Отчёт о стоимости размещения по товарам — как источник хранения вместо разнесения по выручке.
11. Время сборки месяца на Raspberry Pi.

## 12. Слабые места

- Восемь таблиц и конвейер сборки дороже расчёта на чтении; оправдание — построчная объяснимость и дешёвое чтение на Pi.
- Корректность зависит от вызовов `markStale`; страховка — ежедневная пересборка трёх месяцев и сравнение `totals` с `prev_totals`.
- Выручка признаётся по дате операции, а не по отчёту о реализации; расхождение видно в сверке, но в прибыли не устраняется.
- Товарная прибыль точна настолько, насколько мала доля разнесённого по выручке.
- Себестоимость Ozon оценочная до порции 10. Налог — оценка, ОСНО не поддержан.
- Бренда и категории в фактах нет; плана для экрана «план/факт» нет.
- Доменных правил `.cursor/rules` в рабочем дереве нет до переустановки сервера.
