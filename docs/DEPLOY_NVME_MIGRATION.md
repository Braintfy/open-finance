# DEPLOY_NVME_MIGRATION.md — перенос прод-системы с microSD на NVMe

> План составлен 2026-08-13. Железо: Raspberry Pi 5 (16 ГБ) в корпусе **Argon ONE V3** с платой расширения M.2 NVMe (шлейф PCIe), диск **Kingston KC3000 1 ТБ (SKC3000S/1024G)**, новый, из коробки.
> Цель: система целиком уезжает на NVMe, microSD можно физически вынуть.
> Базовый деплой и фазы первичной установки — `docs/DEPLOY_RPI5.md`. Рутина обновления — скил `of-deploy-pi`.
>
> **Статус: ВЫПОЛНЕНО 2026-08-13.** Система работает с NVMe (`/dev/nvme0n1p2`, 938 ГБ, занято 8,3 ГБ), microSD оставлена как аварийная копия.

## Почему это стоит сделать

microSD — самое слабое место конструкции: на ней сейчас живут прод-база Postgres, секреты и код. У карт ограниченный ресурс записи, а Postgres пишет постоянно; при отказе теряется всё разом. NVMe даёт на порядок больший ресурс, кратно быстрее (особенно на случайных операциях, а это ровно профиль БД) и снимает главный риск.

Отдельный выигрыш: пересборки Next.js на Pi занимают ~3 минуты, значительная часть — дисковый ввод-вывод.

## Что важно знать про это конкретное железо

- **PCIe у Pi 5 — одна линия.** KC3000 — Gen4 x4-диск, то есть он заведомо быстрее, чем шина. Ждать 7000 МБ/с не нужно: практический потолок — около 450 МБ/с на Gen2 и до ~900 МБ/с на Gen3. Для нашей нагрузки этого более чем достаточно.
- **Gen3 официально не поддерживается.** `dtparam=pciex1_gen=3` обычно работает, но у части плат и шлейфов даёт ошибки шины. Начинаем с Gen2 (по умолчанию), Gen3 включаем только после того, как система стабильно поработает — и откатываем при первых же ошибках в `dmesg`.
- **Питание.** KC3000 — производительный диск с заметным пиковым потреблением. Обязателен официальный БП 27 Вт; при просадках Pi начнёт троттлить или ронять диск. Проверять `vcgencmd get_throttled` (ожидаем `0x0`).
- **Нагрев.** В закрытом корпусе NVMe греется; Argon ONE V3 активно охлаждается, но за температурой диска стоит последить в первые дни.
- **Совместимость.** Плата Argon работает не со всеми моделями M.2; KC3000 в списках совместимости встречается, но подтверждать нужно фактом — диск должен появиться в `lspci` и `lsblk`.

## Порядок работ

### 0. Бэкапы до всякого касания диска

Это прод: там боевая база, секреты и рабочий VPN-конфиг. **Снимаем на Mac, а не на сам Pi.**

```bash
# База
ssh -i ~/.ssh/openfinance_pi firay@<IP> \
  'docker exec openfinance-postgres pg_dump -U openfinance_user -d openfinance -Fc' \
  > ~/pi-backup-$(date +%F)/db.dump

# Секреты и конфиги (БЕЗ них восстановленный дамп не расшифрует креды Ozon/IMAP)
scp -i ~/.ssh/openfinance_pi firay@<IP>:/home/firay/open-finance/.env.production  ~/pi-backup-$(date +%F)/
ssh -i ~/.ssh/openfinance_pi firay@<IP> 'sudo cat /usr/local/etc/xray/config.json' > ~/pi-backup-$(date +%F)/xray-config.json
ssh -i ~/.ssh/openfinance_pi firay@<IP> 'sudo tar cz -C /etc nginx systemd/system/open-finance.service systemd/system/of-xray-apply.*' \
  > ~/pi-backup-$(date +%F)/etc-configs.tgz
```

Хранить бэкап секретов отдельно от дампа базы и не класть в репозиторий.

### 1. Проверить, что диск виден

```bash
lspci                      # ожидаем NVMe-устройство на шине
lsblk -o NAME,SIZE,MODEL   # ожидаем nvme0n1 ~1 ТБ, модель KC3000
sudo dmesg | grep -iE 'nvme|pcie' | tail -30
```

Если устройства нет — включить PCIe в `/boot/firmware/config.txt`:

```
dtparam=pciex1
```

и перезагрузиться. Если и после этого пусто — проверять физику: шлейф PCIe вставлен до упора с обеих сторон и правильной стороной, диск дожат в слот и закреплён винтом.

**Форматировать вручную не нужно** — клонирование само создаст таблицу разделов и файловые системы. Диск из коробки может быть размечен под Windows; это не мешает, разметка будет перезаписана.

### 2. Обновить загрузчик и разрешить загрузку с NVMe

```bash
sudo rpi-eeprom-update -a        # обновить прошивку загрузчика
sudo reboot
sudo rpi-eeprom-config --edit    # выставить BOOT_ORDER=0xf416
```

Значение читается **справа налево по одной цифре**: `6` = NVMe, `1` = microSD, `4` = USB, `f` = начать сначала.

- `0xf461` → SD → NVMe → USB → повтор. **Ставим на время подготовки**: пока клона нет, ничего не меняется.
- `0xf416` → NVMe → SD → USB → повтор. **Ставим для проверки после клонирования.** Это и есть безопасный тест: если с NVMe что-то не так, загрузчик сам провалится на карту — вынимать её и лезть в корпус не нужно.

### 3. Клонировать систему

Служб, которые пишут на диск, быть не должно — иначе копия базы окажется несогласованной:

```bash
sudo systemctl stop open-finance
sudo systemctl stop docker
```

Дальше — `rpi-clone` (или `rpi-clone-setup`), он сам создаст разделы, скопирует данные и, главное, поправит `PARTUUID` в `/etc/fstab` и `/boot/firmware/cmdline.txt`:

```bash
sudo rpi-clone nvme0n1
```

**Самая частая ошибка при ручном копировании** — забыть про `PARTUUID`: система клонируется, но при загрузке с NVMe ядро ищет корень по старому идентификатору карты и уходит в панику. Если клонируете вручную (`rsync`), обязательно возьмите новые `PARTUUID` из `sudo blkid` и пропишите их в обоих файлах на NVMe.

После клонирования вернуть службы:
```bash
sudo systemctl start docker && sudo systemctl start open-finance
```

### 4. Проверить загрузку с NVMe

Выключить Pi, **физически вынуть microSD**, включить. Если система поднялась:

```bash
lsblk                              # корень должен быть на nvme0n1p2
findmnt /                          # источник — /dev/nvme0n1p2
systemctl is-active open-finance xray of-xray-apply.path docker
curl -sk -o /dev/null -w '%{http_code}\n' https://localhost/
docker exec openfinance-postgres psql -U openfinance_user -d openfinance -c '\dt' | tail -3
vcgencmd get_throttled              # ожидаем 0x0
```

Если не загрузилась — вернуть карту и разбираться по `dmesg`; система на карте осталась нетронутой, потерь нет.

### 5. После успешного перехода

- Расширить корневой раздел на весь диск, если клонирование этого не сделало (`sudo raspi-config --expand-rootfs` или `parted`+`resize2fs`).
- Убедиться, что TRIM работает: `sudo fstrim -v /` и включённый таймер `fstrim.timer`.
- **Проверить автозапуск всех служб** — отдельно актуально после отключения электричества: `systemctl is-enabled open-finance docker xray of-xray-apply.path`. Если `open-finance` не `enabled` — включить, иначе после каждого сбоя питания приложение придётся стартовать руками.
- Первые дни последить за температурой диска и `dmesg` на предмет ошибок PCIe.
- Только после этого — при желании — попробовать `dtparam=pciex1_gen=3` и снова проверить `dmesg`.
- microSD **сохранить как аварийный образ** хотя бы на неделю: это готовая загрузочная копия рабочей системы.

### 6. Обновить документацию

После переноса поправить `docs/DEPLOY_RPI5.md` (там сказано «пока на microSD, NVMe отдельной фазой») и скил `of-deploy-pi` (координаты и пути не меняются, но исчезает предупреждение про ресурс карты). Записать в `MEMORY.md`, что прод живёт на NVMe.

## Что пошло не так на практике (уроки первого переноса)

1. **`rpi-clone` не умеет NVMe.** Он собирает имена разделов приклеиванием номера (`nvme0n1` + `1` = `nvme0n11`), тогда как ядро использует разделитель `p` (`nvme0n1p1`). В итоге таблицу разделов он создал и растянул корректно, загрузочный раздел отформатировал, а `mkfs` корневого ушёл в несуществующее устройство и молча не сработал. **Вывод: на NVMe клонировать вручную** — `mkfs.ext4` + `rsync -aHAXx --numeric-ids` + правка `PARTUUID`. Это те же действия, но с понятными именами.
   Ещё нюанс: `rpi-clone` отказывается инициализировать чистый диск с флагом `-u`, требуется `-U`.

2. **Автоматического отката на карту НЕ происходит, если ядро с NVMe стартовало.** Загрузчик перебирает устройства только пока не найдёт загрузочное; дальнейшие проблемы (не поднялись службы, отвалился диск) для него уже «успех». Рассчитывать на `BOOT_ORDER` как на страховку от неполной загрузки нельзя — страховка только одна: **нетронутая карта и физический доступ**.

3. **Первая загрузка с нового диска долгая.** У нас она заняла заметно больше обычных 16 секунд: сеть поднялась почти сразу, а службы — существенно позже. Промежуточная картина (`ping` идёт, порт 22 принимает соединение, но SSH рвётся до баннера, сайт молчит) выглядит как «система встала», хотя это просто ещё не закончившаяся загрузка. **Не паниковать раньше 5-10 минут**; сокет SSH слушает systemd, поэтому «открытый порт 22» ничего не доказывает.

4. **Проверять факт, а не гипотезу.** Симптомы совпадали с «диск отваливается от шины PCIe» (известная беда Pi 5), но `dmesg` показал **ноль** ошибок NVMe. Гипотеза была неверной — помог монитор, подключённый к плате.

5. **Консоль состояния на мониторе окупилась немедленно.** Именно она показала, что система жива и работает с NVMe, когда по сети было не достучаться. Ставить её стоит ДО рискованных операций, а не после.

6. **Кириллица в консоли Pi 5 частично не отображается.** Ядро отказывается подгружать шрифты в DRM-консоль (`setfont: Unable to load such font with such kernel version`) при любом размере и наборе. Лечится только заменой подписей на латиницу; на читаемость цифр и статусов не влияет.

## Риски и как они закрыты

| Риск | Что делаем |
|---|---|
| Диск не определится платой | Проверяем до всякого клонирования (шаг 1); при неудаче остаёмся на карте без потерь |
| Несогласованная копия базы | Останавливаем Docker и приложение перед клонированием (шаг 3) |
| Система не грузится с NVMe | `BOOT_ORDER` с приоритетом SD; карта остаётся рабочей копией |
| Нестабильность на Gen3 | Начинаем на Gen2, переключаемся позже и только по факту стабильности |
| Просадка питания | Официальный БП 27 Вт, контроль `vcgencmd get_throttled` |
| Потеря секретов | Отдельный бэкап `.env.production` и конфига Xray **до** начала (шаг 0) |

## Что делать нельзя

Не мигрировать во время работающей синхронизации Ozon (незавершённый job повиснет). Не клонировать «на живую» с работающим Postgres. Не переносить `.env.production` через репозиторий. Не выбрасывать карту сразу после первой успешной загрузки.
